## 13. 演练中发现并已修掉的问题（都是真跑才暴露的）

| # | 症状 | 根因 | 修法 |
| --- | --- | --- | --- |
| 1 | 首次迁移在"导入当前版本"后崩：`id: unbound variable` | `local id="$1" dst="$BBS_HOME/releases/$id"` 同一行，bash 先展开全部 RHS 再赋值，`set -u` 下 `$id` 未定义 | 拆成两行赋值 |
| 2 | 迁移重跑时"包内 jar 与现网一致"校验被跳过 | `versions/latest` 已指向 `releases/current`，`readlink -f` 拿到的是新 release 目录（其下是 `app/`，没有顶层 `bbs-server.jar`） | 解析结果落在 `releases/` 时，回退到 `versions/` 下最新的真实目录做基准 |
| 3 | 进程被中断后 `.deploy.lock` 残留，后续所有部署被拒 | 锁只靠 trap 释放 | owner 里记录 pid，`kill -0` 失败即判定过期并自动清理（打印 WARN） |
| 4 | 在源码仓库里执行 `./deploy.sh` 会落到 `/data/bbs` 并开始迁移 | 自动识别顺序里"有 `/data/bbs` 就用它"先于"这是不是源码仓库" | 加守卫：`SELF_DIR` 有 `bbs-server/pom.xml` 且未指定 `--home` → 打印正确入口并 `exit 2` |
| 5 | 迁移后根目录 `deploy-offline.sh` 仍是旧实现，新包用不了 | 迁移只同步了 `scripts/` | 同步 `scripts/` 后把 `scripts/prod/deploy-offline.sh` 覆盖到根目录（旧文件已进 `legacy/`） |
| 6 | 健康检查日志出现 `HTTP 000000` | `curl ... \|\| echo 000` 在 curl 已输出 `000` 时再追加一次 | 改为 `code=$(curl ...) \|\| code=000` + 空值兜底 |
| 7 | 包体积 52MB，超过 15MB 判据 | `scripts/test/e2e-selenium/target/*.jar` 被打进包 | 打包排除 `*/target`、`*/node_modules`、`*.log` → 8.1MB |
| 8 | （意外但有用）对 WSL 的 `/data/bbs` 触发了一次迁移尝试 | 第 4 条守卫缺失导致 | 在**切换指针前**因"包内 jar ≠ 现网 jar"中止（`972b28e…` vs `bea09f9…`），指针/容器未变；已删除误建的 `legacy/`。**这条正是 fail-closed 的实证** |

## 16. 一条命令化改造后的复验（2026-11-27 11:00 后）

用户反馈"现场不该背四五条命令"，据此把入口收敛为两条用法，并复验：

| 用法 | 场景 | 实测 |
| --- | --- | --- |
| `bash deploy.sh` | 日常升级；无包时只做校验 | 无包分支：`[INFO] 没有待部署的包：只做校验，不改动任何东西` → 21 项 `FAIL=0`，退出 0 |
| `bash deploy.sh once migrate` | 一次性迁移（`tmp` 亦可） | 打印「一次性操作模式（once）」，21 项 `FAIL=0`，包归档方式自动选 `cp`（源在 U 盘/只读挂载时不会被搬走） |
| `bash deploy.sh <包路径>` | 不想让脚本自己找包 | 支持任意路径；`/media/*`、`/run/media/*`、`/mnt/*` 会被识别为"可移动介质" |
| `bash deploy.sh once rollback` | 回滚 | 与 S9 等价（同一实现） |

其它配套：

- `package.sh` 打包结束打印**交付卡**：`需要上传到内网的文件（共 N 项）`。
  实测两次：`deploy.sh` 变化时 N=2，未变化时 N=1（`dist/.deploy.sh.sha256` 记录上次交付的入口哈希）。
- 包自动发现顺序：部署根 → 当前目录 → `dist/` → U 盘挂载点；`bbs-full-*` 不参与日常自动选取。
- 现场只需记两条：`bash deploy.sh`（日常）/ `bash deploy.sh once <动作>`（一次性）。

## 18. S12 回滚安全性修复与「撤销迁移」复验（2026-11-27 15:00 后）

| 缺陷 | 现象 | 修法 | 判据 |
| --- | --- | --- | --- |
| `previous` 被写成"刚失败的版本" | 失败自动回滚后 `current.json.previous` 指向坏版本，下次 rollback 往坑里跳 | 写 `current.json` 前用 `sanitize_prev()` 过滤：等于本次失败版本或带 `.failed` 的一律置空 | 同版本修复后 `previous=[]`；S10 自动回滚后 `previous=[]` |
| 坏版本可被再次选为目标 | 人工 `--to` 也能选中坏版本 | 失败时在 `releases/<id>/` 打 `.failed`；rollback 命中即拒绝（`--force` 放行），验证成功清除 | `.failed` 存在且 rollback 拒绝 |
| 迁移成功后无法撤销 | `rollback` 报"没有上一版" | `previous` 为空且 `versions/` 有旧目录时走「撤销迁移」：指回旧目录、删 `releases/current`、旧布局重建 + 专用验证 | rc=0；容器挂 `versions/<ts>/bbs-server.jar`；三端点 200 |
| 迁移顺序 | 先切指针再起容器，容器失败时指针已变 | 改为**先起新容器、成功后再切指针** | S1/S12 复跑 `FAIL=0` |

复验输出（最终字节 `deploy.sh BBCE5503…09E1`）：

```
# 撤销迁移
[WARN] 没有上一版 release；检测到迁移前的旧布局，执行「撤销迁移」→ 20261126_102549
[ OK ] 旧布局：挂载探针通过
[ OK ] 旧布局：三端点 200
[ OK ] 已撤销迁移（容器回到 current/... 旧挂载，releases/ 保留）
current=…/versions/20261126_102549

# 再迁移回来
[ OK ] 迁移完成：20261126_102549-291ae68（旧 versions/ 原样保留）
===== 结果: FAIL=0 =====
```

> 迁移后容器挂真实路径，`DEPLOY.md` §10.5 的
> `ln -snf <旧ts> versions/latest && podman restart` **不再能回滚运行中的代码**；
> 迁移后一律用 `deploy.sh once rollback`。
