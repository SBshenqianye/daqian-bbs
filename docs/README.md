# docs 索引：人看什么、agent 看什么

> 一句话：**代码是轴，文档分两端**——左端是需求与设计（从会话/决策来），右端是实现事实（从代码来）。
> 判断一份新文档该放哪，只看"它会不会因为代码改动而失效"。

## 目录契约

| 目录 | 给谁 | 放什么 | 不放什么 |
| --- | --- | --- | --- |
| `human/需求/` | 人 | 需求分析、需求更新计划、功能需求与设计报告 | 代码细节、端口、命令 |
| `human/设计/` | 人 | 权限架构、审计日志、权限组实现说明、角色权限清单 | 已落地代码的逐行解释 |
| `human/手册/` | 人 | 用户手册（现行版）、手册更新流程 | 内部实现 |
| `human/验收/` | 人 | 验收清单、测试报告 | 计划稿（进 archive） |
| `human/运维/` | 人 | 运维能力规划、迁移/部署 prompt | 一次性排障记录（进 `.trash/`） |
| `agent/` | agent | 操作性上下文：编码约定、目录契约、迁移与回滚判据 | 需求争论、方案取舍（那是 human 的事） |
| `assets/` | 两者 | 图标、设计稿等二进制资产（`level-icons/`） | 文档正文 |
| `data/` | 两者 | 可复现的数据材料（敏感词库、组织架构导入） | 运行期数据（在部署根） |
| `archive/` | 人 | 已执行完的计划、过期验收 SQL（`docs/archive/release-check/`）、旧待办 | 仍在生效的规范 |
| `../.trash/` | 无 | 待删（gitignore，确认无用后物理删除） | 任何还要引用的东西 |

## 三端关系（金箍棒模型）

```text
   需求（会话总结） ──plan──▶ 设计（决策/取舍） ──落地──▶ 代码（唯一事实）
                                                        │
                                                        └─抽取/校验─▶ 实现文档（agent/ + DEPLOY.md）

   左端：从会话与决策来，允许有"为什么"
   右端：从代码来，只写"是什么/怎么做"，不写"为什么"
   完成度 = 两端之间的间距：设计承诺的项逐条落到实现事实里，间距越小越接近完成
```

右端的落地方式（唯一一处手写例外是"为什么"）：

- `docs/agent/实现事实.md` 由 `scripts/dev/doc-check.mjs` 从代码生成，**不手改**；
- 提交前跑 `npm run doc:check`，代码改了而文档没更新 → exit 1 并打印差异；
- 后续 `--delta`（未实现）：扫描 `docs/human/设计/*.md` 的 `- [ ]` 条目，与实现事实比对，输出"已实现/未实现 + 百分比"。

规则：

1. **右端不许凭记忆手写**：`agent/` 与 `DEPLOY.md` 里的事实（端口、路径、命令、目录）必须能在代码里找到；
   找不到就说明文档过期，改代码或改文档，不要两边都留着。
2. **左端不许从代码反推**：需求与设计写的是"当时为什么这么定"，代码里没有这个信息，别试图生成。
3. **一份事实只写一处**：同一个数字（如 60000）只在一个地方定义，其它地方引用它。
4. **过期不删，先降级**：失效的计划/验收材料进 `archive/`；确定没用的进 `.trash/`，一周后再物理删。

## 新增文档时问自己 4 个问题

1. 它会不会因为**代码改动**而失效？会 → `agent/`（或 DEPLOY.md）；不会 → `human/`。
2. 它回答的是"为什么这么做"还是"具体怎么做"？前者 `human/设计`，后者 `agent/`。
3. 它现在还有效吗？已执行完 → `archive/`。
4. 它含密钥/内网地址/个人信息吗？含 → 不进 git（`.trash/` 或保持 ignore）。
