## 二、逐条分析

### #1 [bug] 举报时未反馈 —— 根因明确，改动小

**现状核实**：`BBSReportDialog.vue` 提交成功仅 `$emit('submitted')` + 关闭弹窗，未调用 `handleResponse`；`shared/api-interceptor.js` 已明确取消"拦截器自动弹成功 Toast"（成功提示统一走 `handleResponse`），导致举报成功后用户**零反馈**。后端目前只有"举报被核实"（`report_confirmed`）时才发通知，提交时无任何确认通知。

**方案建议**：
1. 提交成功弹一次性提示（如"举报已提交，管理员会尽快核实处理"），关闭弹窗后展示；
2. 后端 `submitReport` 给举报人补一条 `report_received`（已收到举报）通知，便于"我的举报"页面有迹可循；
3. 注意与拦截器/`handleResponse` 的提示策略一致，避免双弹。

---

### #2 [bug] 管理员能通过自己的举报请求 —— 权限漏洞，P0

**现状核实**：`ReportServiceImpl.reviewReport` 仅校验"举报存在、状态 pending"，**未校验 reporterId ≠ reviewerId**；`submitReport` 也未排除管理员账号。管理员可"自己举报 → 自己审核通过"：对目标扣分的同时自己拿 +2 举报奖励，规则可被滥用。

**方案建议**：
1. 后端审核时校验：举报人不得审核自己的举报（reporterId == reviewerId 直接拒绝）；
2. 管理员账号提交的举报不参与 +2 奖励（或直接禁止管理员举报普通内容）；
3. 关键操作记录审计日志（谁举报、谁审核、扣分依据）。

---

### #3 [bug] 恶意举报驳回后缺少扣分窗口 —— 功能缺失，P1

**现状核实**：管理端"驳回"仅置状态 `rejected`，无扣分入口；`reviewReport` 的 rejected 分支也无扣分逻辑。用户端弹窗文案已声明"恶意虚假举报将被扣分"，但管理端没有对应能力，**文案与能力不一致**。

**方案建议**：
1. 驳回弹窗扩展为可选项：勾选"恶意举报"并填写分值（建议默认 -5，走数据字典可配置）；
2. 后端支持"驳回 + 恶意举报扣分 + 通知举报人 + 积分日志"；
3. 与 #2 联动：管理员驳回自己的举报同样拦截。

---

### #4 [feat] 特殊标签名称可配置 —— 已确认硬编码，P2

**现状核实**：`ArticleController.java:530` 采纳建议校验硬编码 `"建议反馈".equals(label.getLabelName())`；`ArticleServiceImpl.enrichWithSuggestionAdopted`（约 405 行）同样按"建议反馈"名称判断。**标签改名后采纳功能即失效**，与用户描述完全一致。

**方案建议**（推荐方案一）：
1. **标签表加用途标记字段**（如 `label_type`：suggestion / question / normal），业务按标记判断，与名称解耦；需同步 4 个 SQL 文件（init/upgrade × MySQL/PG，遵循项目迁移规范）；
2. 或系统配置项存"建议反馈标签 ID"，管理员改标签名不动功能，但换标签需改配置；
3. 顺带全局排查其他按标签名硬编码的业务点（搜索 `labelName` 使用处），一并治理。

### #5 [bug] 帖子管理标签筛选 PG 报错 —— 根因明确，P0

**现状核实**：链路为 前端 `ArticlePage.vue` 把 `labelId` 以 `String(label.labelId)` 提交 → 后端 `ArticleController.java:462` 强制 `String labelId = (String) params.getOrDefault(...)` → `ArticleMapper.xml` 中 `AND a.article_label_id = #{labelId}` 与 PostgreSQL integer 列比较 → **PSQLException: operator does not exist: integer = character varying**。MySQL 隐式转换不报错，PG 严格类型检查即炸。

**方案建议**：
1. 后端将 `labelId` 解析为 `Integer`（空串/非数字按 null 处理），XML 参数随之成为整型；
2. 前端可保持字符串提交（后端兜底转换），但后端必须强转而非直接 `(String)` 强转；
3. 修复后在 PG + MySQL 双库回归验证筛选与统计。

### #6 [bug] 直接发布（新帖）间歇性失效且无提示 —— 无法稳定复现，静默缺陷确定，P0

**用户实测（2026-09-21，两次）**：第一次"直接发布"失败（刷新后帖子不存在、零提示）；重新测试后**发布恢复正常**——属间歇性问题，无法稳定复现。

**代码核实结论**：
- 前端所有失败路径零提示（`silent:true` + catch 仅 `console.warn`）——**确定缺陷**；
- 已排除：业务校验（会弹窗）、摘要超长（前端截断 250）、附件空数组、标签 FK（无约束）、`ContentQualityUtil`/`SensitiveWordUtil` 抛异常；
- 间歇性特征 + 帖子未入库 → 后端 `publish` 执行中偶发异常（`save` 及其前字段处理）或前端偶发 JS 异常（`syncContent`/`htmlToMd`）均为候选，需等下次复现时取证。

**修复方案（必须做，与根因无关）**：
1. 前端：catch 必弹提示 + `handleResponse` 失败提示，让错误显性化；
2. 后端：`publish` 补异常日志；下次复现时错误自动暴露，按堆栈定位具体环节。

### #7 [bug] 帖子管理统计数字不准确 —— 根因明确，P1

**现状核实**：`ArticlePage.vue` 中 `tabCounts`（done/pending/featured）在 data 中初始化为 0，**全代码无任何赋值/拉取逻辑**，tab 上的数字恒为 0。"分类筛选是假的"不准确——分类切换本身真实生效（已审核 `enable=1`、未审核 `enable=0`、精华帖调 `/admin/featured/list`），**假的只是统计数字**。

**方案建议**：
1. 后端新增统计接口（如 `/admin/article/counts` 返回 enable=1、enable=0、is_featured=1 三个计数），口径与列表一致（含 is_delete=0）；
2. 前端 `mounted` 与筛选条件变化后刷新 tabCounts；
3. 数字与当前筛选（关键词/标签/时间）是否联动，需定口径（建议：tab 数字=该分类全局计数，与筛选解耦）。

### #9 [bug] 导出积分排名 excel 为空 —— 已定位根因（容器无字体 NPE）并修复，P1

**根因（2026-09-22 通过后端日志锁定）**：导出请求在后端抛 java.lang.NullPointerException，完整堆栈指向：

`
ArticleController.exportPointsRank:645 → ExcelWriter.write(sheet1)
  → SXSSFWorkbook.createSheet → AutoSizeColumnTracker.<init>
    → SheetUtil.getDefaultCharWidth → java.awt.font.TextLayout
      → sun.awt.X11FontManager.<init> → FontConfiguration.readFontConfigFile
        → NPE
`

**机制**：EasyExcel 默认用 POI 的 SXSSF 写 Excel，创建每个 sheet 时都会调用 java.awt 测量默认字符宽度；内网容器（Linux 无图形环境、未装 fontconfig/字体）中 java.awt 字体子系统初始化即 NPE → 整个导出中断。异常发生在设置 Content-Type: xlsx 之后，GlobalExceptionHandler 无法把错误改回 JSON（No converter for ResultBean with preset Content-Type xlsx）→ 浏览器收到 **200 + Content-Length 0 + 0 字节文件**，表现为"导出 excel 为空"。

**排除过程**（数据侧全部正常）：
- 积分日志 36 条、时间 06-30~09-21、无撤销标记；
- 个人排名"全部"范围必然返回 2 行（user 2=21 分、user 3=200053 分），F12 实测 /common/personalPointsRank 响应 list 确有 2 条；
- is_ranking_selected=1 单位大量存在，单位排名过滤正常；
- 页面请求参数正确（startTime=2000-01-01、endTime=2026-09-22）。

**修复（已完成，2 处）**：
1. ArticleController.exportPointsRank：EasyExcel.write(...).inMemory(true).build() —— 改用 XSSFWorkbook，创建 sheet 不再触发 java.awt 字体测量；
2. SensitiveWordController 敏感词导出（同类风险）同样加 .inMemory(true)。

**部署侧建议（治本，防止其他 POI 功能再炸）**：容器内安装 ontconfig 和中文字体：
`ash
# Debian/Ubuntu 系
apt-get update && apt-get install -y fontconfig fonts-dejavu-core
# CentOS/RHEL 系
yum install -y fontconfig dejavu-sans-fonts
`
可在 scripts/deploy/offline.sh 的容器构建步骤中追加。

**验证方式**：重新构建部署后导出积分排名 → 三个 sheet 应分别有单位排名（5140401/402/403）、个人排名（user 2/3）、积分明细（36 条）。

**补充修复（2026-09-22，表头结构错误）**：导出文件能正常打开后，发现表头竖排（单列 6 行）而数据横排（第 7 行起），字段与数据错位。根因：EasyExcel `head(List<List<String>>)` 的外层 List 每个元素代表**一列**、内层 List 代表该列自上而下的多行表头；原 `unitRankHeader/personalRankHeader/pointsLogHeader` 把全部字段塞进**同一个内层 List**，被写成 1 列多行。修复：改为每列一个单元素 List（6/8 列 × 1 行）。已用 EasyExcel 3.3.4 实测对比：旧写法 → 表头 A1:A6 竖排、数据从第 7 行；新写法 → 表头第 1 行横向、数据从第 2 行一一对应。`SensitiveWordController`/`UserServiceImpl` 导出均用 `@ExcelProperty` 注解类，无此问题。已编译通过，待重新部署验证。

**补充修复（2026-09-22，导出文件名误解）**：用户选"个人排名"导出时，文件名为"积分排名_个人_…"但第一个 sheet 固定是"单位排名"，打开默认显示单位数据，被误认为"导出个人也是单位的"。**用户拍板**：三个 sheet 固定顺序保留（单位排名 → 个人排名 → 积分明细），不改 sheet 顺序；**文件名不再随当前 tab 变动**（去掉"单位/个人"标识，避免与多 sheet 内容产生误解）。修复：前端 `BBSPoints.vue` 导出文件名统一为 `积分排名_{startTime}_{endTime}.xlsx`。后端已恢复固定 sheet 顺序（与 #9 定案一致），编译通过，待重新部署验证。

### #13 [bug] 任命版主时跳出两个弹窗 —— 根因基本明确，P1

**现状核实**：后端返回业务错误（code 500）时链路为：
1. `api-interceptor.js` 对 code 500 先弹一个 warning（后端 message）；
2. 同时该分支 `return`（返回 undefined），`ModeratorPage` 的 `handleResponse(undefined)` 判定失败再弹一个 error（前端写死的 `errorMsg: '任命失败'`）；
3. 两条文案不同，`showUniqueMessage` 去重失效 → **双弹窗**。

此问题影响所有"拦截器弹 500 + handleResponse(undefined) 再弹 errorMsg"的调用点，任命版主只是先暴露的。

**方案建议**：
1. 拦截器 500 分支改为 `return success.data`（让调用方统一走 handleResponse），或 handleResponse 对 undefined 且已弹过的情况不再弹；
2. 统一"一请求一提示"策略，全站排查 `handleResponse` 调用点；
3. 回归测试：造一个 500 场景验证单弹。

### #14 [feat] 违规管理添加取消违规 —— 已确认，P2

3. 与申诉流程衔接：申诉通过后提供"自动回滚"或"手动取消"两种模式（需产品定口径：申诉通过是否自动加回积分——现有 appeal 通过逻辑需核对）。
