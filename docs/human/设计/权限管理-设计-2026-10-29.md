# 大千智荟 BBS 权限管理（权限组）设计

> 状态：Phase A（只读权限矩阵）已于 2026-11-02 实施；Phase B/C（grant-only）与 Phase D 后端权限点已于 2026-11-02 实施；revoke 与前台按钮全量控制暂不实施  
> 日期：2026-10-29（2026-11-02 更新）  
> 目标：在现有“固定角色 + 权限点 + 数据范围”基础上，增加可视化权限组、拖拽配置、预存方案和细粒度前台动作权限。

## 1. 背景

当前权限模型：

- 账号角色：`USER / ADMIN / SUPER_ADMIN`；
- 权限点：`Permission` 静态映射到角色；
- 数据范围：`BOARD_MODERATOR(labelId)`；
- 自审批：`SelfApprovalPolicy`。

问题：

- 角色权限矩阵写死在代码中，调整需要发版；
- 无法快速创建“版主专用管理员”“只读运营”“内容审核员”等组合；
- 无法控制用户前台动作（发帖、评论、回复、举报、申诉、上传等）；
- 版主 + 管理员仍拥有 ADMIN 全局权限，不能实现“版主登录只看到板块页面”。

## 2. 设计目标

1. 固定角色保留，作为默认权限基线；
2. 新增“权限组”作为可配置覆盖层；
3. 支持拖拽把权限点分配到权限组；
4. 支持保存/切换预设方案（如“默认管理员”“版主模式”“只读运营”）；
5. 支持前台动作权限点，例如 `post:create`、`comment:create`、`reply:create`、`report:submit`、`appeal:submit`、`upload:file`；
6. 权限变更实时生效（每次请求重新计算，或短 TTL 缓存）；
7. 默认拒绝，权限组只做“额外授予/收回”的白名单管理；
8. 全量审计：谁在什么时候改了哪个组、哪些权限。

## 3. 概念模型

```text
AccountRole（固定基线）
  ├── USER
  ├── ADMIN
  └── SUPER_ADMIN

PermissionGroup（可配置权限组）
  ├── 名称、编码、描述
  ├── 生效范围：全局 / 仅管理后台 / 仅前台
  ├── 权限点集合
  └── 数据范围（可选：ALL / BOARD_MODERATOR）

UserPermissionGroup（用户-权限组）
  ├── userId
  ├── groupId
  └── 优先级（多组叠加时的覆盖顺序）

PermissionPreset（预存方案）
  ├── 名称
  ├── 权限组快照 JSON
  └── 可一键应用/回滚
```

生效权限计算：

```text
effectivePermissions =
  roleDefaultPermissions(AccountRole)
  + grantedByGroups
  - revokedByGroups
```

> 是否允许“收回”高于角色的权限，需要产品决策。建议：普通管理员不能被权限组提升为超管；超管权限只能由超管授予。

- `appeal:review`
- `moderator:*`
- `adopt:review`

### 4.2 新增前台动作权限
建议新增权限点（前缀 `front:` 或直接动作名）：

| 权限点 | 说明 |
|---|---|
| `post:create` | 发帖 |
| `post:update:own` | 编辑自己的帖子 |
| `post:delete:own` | 删除自己的帖子 |
| `comment:create` | 评论 |
| `reply:create` | 回复 |
| `report:submit` | 提交举报 |
| `appeal:submit` | 提交申诉 |
| `moderator:complain` | 投诉版主 |
| `upload:file` | 上传图片/附件 |
| `profile:update` | 修改个人资料 |
| `password:update` | 修改密码 |

> 这些权限默认授予 `USER` 及以上角色；权限组可对特定用户收回（例如禁言/限制发帖可复用现有 `post_restricted`，权限组用于更细的场景）。

新增管理后台一级菜单：**权限管理**（仅 `SUPER_ADMIN` 可见，或新增 `permission:manage` 权限点）。

页面布局：

```text
┌──────────────────────────────────────────────────────────┐
│ 权限管理                                      [预设方案 ▼] │
├──────────────┬──────────────────────┬────────────────────┤

│              │                      │                    │
│ 默认管理员    │ 管理端                │ 名称：版主模式      │
│ 版主模式      │  ├─ 用户管理          │ 编码：moderator     │
│ 只读运营      │  │   ├─ user:read     │ 数据范围：板块      │
│ + 新建组      │  │   └─ user:update   │ 前台动作：...       │
│              │  ├─ 配置管理          │ [保存] [另存预设]   │
│              │  └─ 内容管理          │                    │

│              │  ├─ 发帖              │                    │
│              │  └─ 评论              │                    │
└──────────────┴──────────────────────┴────────────────────┘
```

交互：

1. 左侧权限组列表，支持拖拽排序；
2. 中间权限树按“管理端 / 前台 / 数据范围”分组；
3. 从“可用权限”拖到权限组，或勾选；
4. 右侧显示组详情、数据范围、前台动作；
5. 顶部“预设方案”支持：
   - 保存当前配置为预设；
   - 一键应用预设；
   - 导出/导入 JSON；
   - 查看历史版本并回滚；
6. 保存前展示 diff（新增/移除权限）；
7. 权限变更后，受影响用户下次请求生效（或强制刷新 token）。

## 8. 实施阶段

### Phase A：只读权限矩阵
- 新增权限管理页面，只展示当前角色/用户有效权限；
- 不改鉴权逻辑，用于核对现状。

### Phase B：权限组 CRUD
- 新表、接口、页面；
- `AuthorizationService` 支持权限组覆盖；
- 登录响应 `permissions` 返回有效权限。

> 2026-11-02 实施口径：**grant-only**。权限组只与角色基线做并集，不收回角色基线；`bbs_permission_group_item.effect` 保留字段但只写 `grant`。数据范围仍由账号角色与 `bbs_board_moderator` 决定，权限组只引用、不覆盖。

### Phase C：拖拽 + 预设
- 权限树拖拽；
- 预设保存/应用/版本回滚；
- 审计日志。

### Phase D：前台动作权限
- 发帖/评论/回复/举报/申诉/上传接入权限点；
- 前端按钮 `v-permission`，后端方法级校验。

> 2026-11-02 实施口径：新增 `post:create`、`post:update:own`、`post:delete:own`、`comment:create`、`comment:delete:own`、`reply:create`、`reply:delete:own`、`report:submit`、`appeal:submit`、`moderator:complain`、`upload:file`、`profile:update`、`password:update`，默认授予 USER 及以上角色；关键前台写接口已接 `@PreAuthorize("@authz.hasPermission(...)")`。bbs-ui 仅对发帖入口/发布按钮做了权限点控制，其余按钮逐步补齐。

## 9. 风险与约束

1. **权限提升风险**：权限组不能绕过“仅超管授予管理员/超管”的硬规则；
2. **缓存一致性**：权限变更需清理缓存或短 TTL；
3. **多组叠加**：必须定义优先级和 grant/revoke 冲突规则；
4. **数据范围**：权限组的数据范围不能替代 `bbs_board_moderator`，只能引用；
5. **审计**：每次变更必须记录操作人、前后 diff；
6. **回滚**：预设方案需支持版本快照，避免误配置无法恢复；
7. **性能**：有效权限计算可缓存到用户会话，但每次请求仍需轻量校验。

## 10. 与当前“版主菜单”问题的关系

当前版主不是账号角色，管理员 + 版主仍拥有 `ADMIN` 全局权限。  
要实现“版主登录只看到帖子管理/违规/举报/采纳/精华”等板块页面，推荐方案：

1. 新增“版主模式”权限组（或账号类型）；
2. 该组只授予板块范围相关权限点；
3. 管理后台菜单按有效权限过滤；
4. 后端对全局接口继续做角色/权限点校验，不能只靠前端隐藏。

该能力属于本次设计范围，暂不实施。

## 11. 候选方案：版主角色化（推荐后续实施）

### 11.1 结论

“版主不是账号角色，只是板块数据范围”在技术上成立，但在产品/UI 上确实容易造成混乱：

- 用户看到的是“版主”，系统里却是 `ADMIN + bbs_board_moderator`；
- 管理员 + 版主仍拥有 ADMIN 的全局菜单和全局权限；
- 不任命板块时，版主身份没有任何可见效果；
- 登录、菜单、权限、数据范围四者语义不一致。

建议采纳“版主角色化”：

> 新增 `MODERATOR` 账号角色；版主可以登录管理后台；有板块时只看到/操作本板块内容，没有板块时进入管理后台但业务页面为空，不回退为普通用户。

### 11.2 角色模型

```text
USER       普通用户
MODERATOR  版主（管理后台仅板块范围）
ADMIN      管理员（全局管理）
SUPER_ADMIN 超级管理员
```

`user_type` 建议扩展为：

| user_type | 角色 |
|---|---|
| `1` | USER |
| `4` | MODERATOR |
| `2` | ADMIN |
| `3` | SUPER_ADMIN |

> 不复用 `2` 表示版主，避免与现有管理员数据冲突；`4` 为新增值。

有效角色优先级：

```text
SUPER_ADMIN > ADMIN > MODERATOR > USER
```

一个账号只有一个账号角色。`ADMIN + 板块` 仍按 ADMIN 全局处理；如需要“只能管板块的管理员”，应使用 MODERATOR，而不是给 ADMIN 绑板块。

### 11.3 权限设计

`MODERATOR` 默认权限：

- `admin:access`
- `dashboard:read`（版主工作台）
- `article:read`
- `article:review`
- `article:delete`
- `article:feature`
- `adopt:review`
- `featured:recommend`
- `report:review`
- `violation:review` / `violation:add` / `violation:cancel`

不授予：

- `user:*`
- `config:*`
- `points:adjust`
- `moderator:manage`
- `moderator:complaint:review`
- `user:grant:admin`

数据范围：

- `MODERATOR` 的所有内容操作必须通过 `canModerateBoard(userId,labelId)`；
- 没有有效板块时，仍可登录管理后台，但所有业务列表/操作返回空或 403，不显示可操作内容；
- 有多个板块时，可管理多个板块；
- 跨板块操作返回 403。

### 11.4 登录与菜单

- `channel=02` 登录：
  - ADMIN / SUPER_ADMIN：允许；
  - MODERATOR：允许进入管理后台，即使当前没有板块；没有板块时业务页面为空；
  - USER：拒绝。
- 登录响应：
  ```json
  { "role": "MODERATOR", "permissions": [...], "boardScopes": [{ "labelId": 1 }] }
  ```
- 菜单：
  - 系统首页 / 帖子管理 / 采纳审批 / 精华审批 / 举报管理 / 违规管理；
  - 不显示用户管理、标签管理、配置管理、积分排名、组织管理、敏感词管理、版主管理、版主投诉。
  - 无板块时：仍显示业务菜单，但列表为空、操作 403，并提示“尚未分配板块，请联系管理员”。
- 路由 `meta.permission` 和方法级权限双重校验；前端隐藏不是安全边界。

### 11.5 版主任命/撤销生命周期

- 任命：
  - 目标用户当前为 USER：设置 `user_type='4'`；
  - 目标用户当前为 ADMIN/SUPER_ADMIN：保持原角色（全局管理员）；
  - 目标用户已有同板块有效任职：拒绝重复任命。
- 撤销：
  - 将该板块 `status=0`；
  - 若用户角色为 MODERATOR 且已无任何有效板块：保留 MODERATOR 角色，仍可登录管理后台，但业务页面为空；
  - 若仍有其他板块：保持 MODERATOR。
- 重新任命：复用 `status=0` 历史记录（现有逻辑）。

### 11.6 迁移策略

1. 新增 `vXXX-moderator-role` 迁移：
   - 将“当前 user_type=1 且存在有效板块任职”的用户改为 `user_type='4'`（需产品确认）；
   - 将“当前 user_type=2 且存在有效板块任职”的用户保留 ADMIN，除非产品明确要转为 MODERATOR；
2. 初始化 SQL 增加 `user_type='4'` 说明；
3. 前端角色标签增加“版主”；
4. 管理后台用户管理页增加角色选项（仅超管可设置 ADMIN；MODERATOR 由版主任命流程自动设置）；
5. 旧 Token 继续可用，权限每次请求实时计算。

### 11.7 影响范围

- `AccountRole`、`Permission`、`User.getAuthorities`
- `SecurityConfig`：`/admin/**` 增加 MODERATOR，同时按路径/方法限制全局接口
- `UserServiceImpl.login`、`adminAddUser`、`adminUpdateUserDetail`
- `BoardModeratorServiceImpl.appoint/dismiss`
- 前端 `adminStore`、路由、Sidebar、用户管理角色选项
- 测试：权限矩阵、登录、菜单、板块隔离、生命周期
- 数据迁移：四文件同步

### 11.8 待产品确认

1. 是否将现有 `user_type=1` 的有效版主自动升级为 MODERATOR？（建议：是，否则升级后仍无法登录管理后台）
2. 现有 `ADMIN + 版主` 是否保留 ADMIN 全局权限？（建议：保留，避免误降权）
3. 是否允许 MODERATOR 查看本板块举报/违规列表？（建议：是，但仅本板块）
4. 版主无板块时保留 MODERATOR 角色、允许登录但页面为空（已按此调整，不再自动降级）
5. 是否正式废止“版主必须同时是管理员”的旧规则？（建议：废止；角色化后不再需要）

### 11.9 版主管理页编辑功能

在现有“版主管理”页面增加“编辑板块”：

- 列表每行增加“编辑”按钮；
- 弹窗展示该用户当前板块（多选）和全部可任命板块；
- 保存时对比差异：
  - 新增板块 → 调 `appoint`；
  - 移除板块 → 调 `dismiss`；
  - 保留板块不变；
- 后端建议新增 `POST /admin/moderator/updateBoards`，参数 `{ userId, labelIds, operatorId }`，由服务端按差异执行并返回新增/移除结果；
- 校验：积分≥300、板块存在、重复任命拦截、撤销后重任命复用历史记录；
- 权限：仅 `moderator:manage`（ADMIN/SUPER_ADMIN）；
- 审计：记录操作人、用户、before/after 板块集合。
