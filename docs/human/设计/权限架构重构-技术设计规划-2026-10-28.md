# 大千智荟 BBS 权限架构重构——技术设计规划书

> 文档版本：v1.0  
> 编写日期：2026-10-28  
> 适用范围：`bbs-server`、`bbs-admin-ui`、`bbs-ui`  
> 文档状态：待评审 / 待实施  
> 关联需求：管理员、超级管理员、版主、普通用户权限梳理与权限架构重构

---

## 0. 摘要

当前系统的权限模型不是标准 RBAC，而是：

1. `bbs_user.user_type` 表示账号级角色（`1` 普通用户、`2` 管理员、`3` 超级管理员）；
2. `bbs_board_moderator` 表示版块级版主任职（按 `label_id` 生效）；
3. 超级管理员在代码中实际通过 `id == 1` 判断；
4. Spring Security 只做登录认证，没有角色授权；
5. 前端管理后台只检查 `sessionStorage` 中是否存在管理员对象，不校验角色；
6. 大量权限判断散落在 Controller / Service / Vue 组件中。

本规划建议将权限体系重构为：

> **固定账号角色 + 权限点 + 数据范围 + 自审批策略** 的轻量授权架构。

不推荐为了四个固定角色直接引入完整的“用户-角色-权限-资源”五表 RBAC，也不推荐按“菱形角色继承”建模，因为版主不是账号角色，而是按板块生效的数据范围。

重构目标不是把现有功能推倒重来，而是：

- 把“登录即可访问管理端”改为“具备管理端权限才能访问”；
- 把 `id == 1` 的超管判断改为角色判断；
- 把版主从“散落的业务标记”改为明确的板块数据范围；
- 把前端菜单/按钮权限与后端权限点对齐；
- 保持现有业务规则和数据结构尽量兼容。

## 1. 背景与问题

### 1.1 现有角色定义

| 角色 | 存储/标识 | 获得方式 | 关键限制 |
|---|---|---|---|
| 普通用户 | `bbs_user.user_type = '1'` | 管理员后台创建或 Excel 导入；前台注册已关闭 | 不能通过 `channel=02` 登录管理后台 |
| 管理员 | `bbs_user.user_type = '2'` | 管理员创建用户时选择“管理员”，或编辑普通用户角色 | 不能操作其他管理员；受自审批限制 |
| 超级管理员 | `bbs_user.user_type = '3'`，代码实际认 `id = 1` | 初始化 SQL 内置 `asiayak`，正常界面无法新增 | 代码中的豁免依赖 `SUPER_ADMIN_ID = 1` |
| 版主 | `bbs_board_moderator` 中 `role_type = 'moderator'`、`status = 1` | 管理员在“版主管理”中任命；累计积分需 ≥ 300 | 不改变 `user_type`，单独任命后不能登录管理后台 |

### 1.2 现有认证链路

- 登录接口：`/common/login`，`channel=01` 为用户前台，`channel=02` 为管理后台。
- `channel=02` 仅拦截 `userType == '1'`，`userType=2/3` 可登录。
- JWT 过滤器：`JwtAuthenticationTokenFilter` 从 Header 解析 Token，重新加载用户并写入 `SecurityContextHolder`。
- `User implements UserDetails`，但 `getAuthorities()` 返回 `null`。
- `SecurityConfig` 中：
  - `/common/**`、`/files/**` 放行；
  - `/common/user/info` 要求登录；
  - `/admin/**` 仅要求 `authenticated()`；
  - 其他请求要求登录；
  - 没有 `hasRole`、`hasAuthority`、`@PreAuthorize`。

### 1.3 现有授权方式

当前权限判断主要分为四类：

1. **账号类型判断**：`userType` 控制登录渠道、用户列表展示、前端角色标签。
2. **硬编码超管判断**：`ConstantUtil.SUPER_ADMIN_ID = 1`，在文章、举报、申诉、版主投诉、精华推荐等业务中做自审批豁免。
3. **版块版主判断**：`BoardModeratorService.isModerator(userId, labelId)`，目前主要用于待审采纳列表过滤。
4. **前端展示控制**：`adminStore`、`UserPage.canCheck()`、`DictPage.isAdminId1`、静态 Sidebar 菜单等。

### 1.4 现实权限矩阵

|  | 普通账号 `user_type=1` | 管理员 `user_type=2` | 超管 `id=1` |
|---|---|---|---|
| 非版主 | 普通用户 | 管理员 | 超级管理员 |
| 某板块版主 | 普通用户 + 版主，但无法登录管理后台 | 管理员 + 版主，待审采纳按板块过滤 | 超管 + 版主，基本无额外意义 |

结论：管理员/超管属于账号角色维度，版主属于板块数据范围维度。两者不是平级角色，不能画成菱形。

### 1.5 问题清单

| ID | 级别 | 问题 | 现状证据 | 影响 |
|---|---|---|---|---|
| A1 | P0 | `/admin/**` 只校验登录，不校验管理员角色 | `SecurityConfig` 中 `.antMatchers("/admin/**").authenticated()` | 普通用户 Token 可直接调用管理端接口 |
| A2 | P0 | 管理后台路由只检查 `sessionStorage.admin` 是否存在 | `bbs-admin-ui/src/main.js` 路由守卫 | 前端权限可被绕过，且没有角色概念 |
| A3 | P0 | `adminAddUser` / `adminUpdateUserDetail` 对 `userType` 无白名单 | `UserServiceImpl` | 直接调接口可写入 `"3"` 等非法角色 |
| A4 | P0 | 普通管理员可以创建管理员、提升普通用户为管理员 | `UserPage.vue` 添加/编辑角色选项；后端无超管限制 | 管理员可自行扩权，违反最小权限原则 |
| B1 | P1 | 超管实际靠 `id == 1`，与 `user_type=3` 不一致 | `ConstantUtil.SUPER_ADMIN_ID` 及多处 `isSuperAdmin` | 改角色不生效；多超管无法支持；代码难维护 |
| B2 | P1 | 版主板块隔离只覆盖待审列表 | `ReplyController.pendingAdopts` 过滤；`approveAdopt` 未校验板块 | 版主可通过已知 ID 审批其他板块内容 |
| B3 | P1 | 版主不是账号角色，单独任命后无法进入管理后台 | `BoardModeratorServiceImpl.appoint` 不修改 `user_type` | 版主权限无法独立使用，必须额外给管理员角色 |
| B4 | P1 | 撤销版主后再次任命同一板块会撞唯一键 | `findByUserAndLabel` 只查 `status=1`；表有 `uk_board_mod_user_label` | 重新任命报错，版主生命周期不完整 |
| B5 | P1 | 操作人参数仍以请求体传入，校验逻辑分散 | 多个 Controller 的 `operatorId/reviewerId/adminId` | 容易漏校验，存在伪造风险 |
| C1 | P2 | 管理后台菜单全量展示，没有按权限过滤 | `Sidebar.vue` 静态 `menuItems` | 无权限用户仍能看到入口，体验与安全边界不一致 |
| C2 | P2 | `bbs-ui` 的 `isModerator()` 判断与真实 `userType` 不匹配 | `userStore.js` 判断 `'moderator'/'admin'` | 死代码，易误导后续开发 |
| C3 | P2 | 管理后台登录不检查首次登录改密 | `Login.vue` 直接跳转；仅用户前台检查 `isFirstLogin` | 新管理员可能长期使用默认密码 |
| C4 | P2 | 缺少统一拒绝日志/审计 | 权限失败无统一记录 | 安全事件难追溯 |

## 2. 设计目标与非目标

### 2.1 设计目标

1. **默认拒绝**：管理端接口默认只允许 `ADMIN` / `SUPER_ADMIN`，公开接口显式放行。
2. **后端为最终边界**：前端隐藏按钮只作为体验优化，不能作为安全依据。
3. **角色与数据范围分离**：
   - 账号角色：`USER`、`ADMIN`、`SUPER_ADMIN`；
   - 板块范围：`BOARD_MODERATOR(labelId)`。
4. **去掉超管魔法值**：业务代码不再直接判断 `id == 1`，统一通过角色/权限服务判断。
5. **权限点可读**：使用 `user:manage`、`article:review`、`adopt:approve` 等权限点，而不是到处写角色字符串。
6. **前后端同源**：登录响应返回角色、权限点、版主板块范围，前端路由/菜单按此渲染。
7. **可渐进迁移**：保留现有接口路径、数据结构、业务规则；分阶段替换，不做一次性大重写。
8. **可测试**：权限矩阵、板块范围、自审批规则均有单元/集成测试覆盖。

### 2.2 非目标

本次重构不包含：

- 完整动态 RBAC（角色/权限可在界面自由配置）；
- 多租户、组织级数据权限；
- SSO、LDAP、OAuth2 接入；
- 细粒度字段级权限；
- 全量审计平台；
- 大规模前端 UI 改版。

### 2.3 设计原则

- **最小权限**：默认无权限，按需授予。
- **单一事实来源**：角色以 `bbs_user.user_type` 为准，版主以 `bbs_board_moderator.status=1` 为准。
- **服务端可信身份**：当前用户 ID 一律从 `SecurityContextHolder` 获取，不信任前端传值。
- **策略与权限分离**：`can()` 判断“能不能做”，`SelfApprovalPolicy` 判断“是否允许对自己做”。
- **兼容优先**：接口路径、返回结构、数据库字段尽量不变；新增字段向前兼容。

## 3. 目标架构

### 3.1 概念模型

```text
AccountRole（全局）
  ├── USER
  ├── ADMIN
  └── SUPER_ADMIN

Permission（权限点）
  ├── admin:access
  ├── user:read / user:create / user:update / user:delete
  ├── user:grant:admin
  ├── config:read / config:write
  ├── article:read / article:review / article:delete / article:feature
  ├── article:suggestion:adopt
  ├── report:review
  ├── appeal:review
  ├── moderator:manage
  ├── moderator:complaint:review
  ├── adopt:review
  ├── featured:recommend / featured:review
  ├── points:read / points:adjust
  └── dashboard:read

DataScope（数据范围）
  └── BOARD_MODERATOR(labelId)
```

### 3.2 角色与权限映射

| 权限点 | USER | ADMIN | SUPER_ADMIN |
|---|---:|---:|---:|
| `admin:access` | ✗ | ✓ | ✓ |
| `user:read` | ✗ | ✓ | ✓ |
| `user:create` | ✗ | ✓ | ✓ |
| `user:update` | ✗ | ✓ | ✓ |
| `user:delete` | ✗ | ✓ | ✓ |
| `user:grant:admin` | ✗ | ✗ | ✓ |
| `config:read` | ✗ | ✓ | ✓ |
| `config:write` | ✗ | ✓ | ✓ |
| `article:read` | 前台可见 | ✓ | ✓ |
| `article:review` | ✗ | ✓ | ✓ |
| `article:delete` | 仅本人可删 | ✓ | ✓ |
| `article:feature` | ✗ | ✓ | ✓ |
| `article:suggestion:adopt` | ✗ | ✓ | ✓ |
| `report:review` | ✗ | ✓ | ✓ |
| `appeal:review` | ✗ | ✓ | ✓ |
| `moderator:manage` | ✗ | ✓ | ✓ |
| `moderator:complaint:review` | ✗ | ✓ | ✓ |
| `adopt:review` | ✗ | ✓ | ✓ |
| `featured:recommend` | ✗ | 仅版主板块 | ✓ |
| `featured:review` | ✗ | ✓ | ✓ |
| `points:read` | 本人 | ✓ | ✓ |
| `points:adjust` | ✗ | ✓ | ✓ |
| `dashboard:read` | ✗ | ✓ | ✓ |

说明：

- `ADMIN` 默认拥有除 `user:grant:admin`、`permission:manage`、`audit:read` 外的管理权限。
- `SUPER_ADMIN` 拥有全部权限，并保留自审批豁免。
- `BOARD_MODERATOR` 不是账号角色，不进入 `AccountRole` 枚举；它作为数据范围参与授权判断。
- 是否允许“普通用户版主”登录管理后台，见第 8 节决策点 D1。

### 3.3 授权决策链

```text
请求
  │
  ├─ 1. JWT 认证：解析 token，加载 User
  │
  ├─ 2. 账号角色：USER / ADMIN / SUPER_ADMIN
  │
  ├─ 3. 粗粒度接口权限：
  │      /admin/** 需要 admin:access
  │      配置写接口需要 config:write
  │      ...
  │
  ├─ 4. 业务权限：AuthorizationService.hasPermission(user, permission)
  │
  ├─ 5. 数据范围：canModerateBoard(userId, labelId)
  │
  ├─ 6. 自审批策略：SelfApprovalPolicy
  │
  └─ 7. 通过 / 返回 403 并记录拒绝日志
```

### 3.4 自审批策略

| 操作 | 普通管理员 | 超级管理员 | 说明 |
|---|---:|---:|---|
| 采纳自己的建议 | ✗ | ✓ | 超管豁免 |
| 审核自己的举报 | ✗ | ✓ | 超管豁免 |
| 审核自己的申诉 | ✗ | ✓ | 超管豁免 |
| 审核自己的版主投诉 | ✗ | ✓ | 超管豁免 |
| 审核自己的精华推荐 | ✗ | ✓ | 超管豁免 |
| 将自己的帖子设为精华 | ✗ | ✓ | 超管豁免；取消精华不受限 |
| 审批自己提问的最佳解答 | ✗ | ✗ | 当前代码对所有人拦截，建议保留 |

自审批规则属于**策略**，不要混进权限点；否则后续会出现“有权限但不能操作自己”的语义混乱。

## 4. 详细设计

### 4.1 角色枚举与 `user_type`

保留 `bbs_user.user_type` 字段，避免大规模数据迁移。新增枚举：

```java
public enum AccountRole {
    USER("1"),
    ADMIN("2"),
    SUPER_ADMIN("3");

    private final String code;
}
```

映射规则：

- `"1"` / `null` → `USER`（`null` 建议迁移时统一补齐为 `"1"`）；
- `"2"` → `ADMIN`；
- `"3"` → `SUPER_ADMIN`；
- 其他值 → 拒绝登录或按 `USER` 处理，并记录告警。

`User.getAuthorities()` 改为返回：

```java
ROLE_USER
ROLE_ADMIN       // user_type = 2 或 3
ROLE_SUPER_ADMIN // user_type = 3
```

超管判断改为：

```java
authorizationService.isSuperAdmin(user); // 内部判断 AccountRole.SUPER_ADMIN
```

禁止再新增 `userId == 1` 的业务判断。初始化 SQL 仍保留 `id=1` 作为引导账号，但代码不再依赖 id。

### 4.2 Spring Security 配置

`SecurityConfig` 调整：

```java
http.authorizeRequests()
    .antMatchers("/common/**", "/files/**").permitAll()
    .antMatchers("/common/user/info").authenticated()
    .antMatchers("/admin/login").permitAll() // 兼容旧接口；若无使用可删除
    .antMatchers("/admin/**").hasAnyRole("ADMIN", "SUPER_ADMIN")
    .anyRequest().authenticated();
```

同时开启方法级安全：

```java
@EnableGlobalMethodSecurity(prePostEnabled = true)
```

注意：

- `/admin/login` 是旧版管理员登录接口，当前前端实际使用 `/common/login`；保留兼容或删除需确认。
- `RestAuthorizationEntryPoint` 返回 401，`RestfulAccessDeniedHandler` 返回 403，沿用现有结构。
- 如果后续允许版主登录管理后台，则 `/admin/**` 需增加 `MODERATOR`，并配合方法级权限，见 D1。

### 4.3 `AuthorizationService`

新增统一授权服务：

```java
public interface AuthorizationService {
    boolean isSuperAdmin(User user);
    boolean hasPermission(User user, Permission permission);
    boolean canModerateBoard(Integer userId, Integer labelId);
    void requirePermission(User user, Permission permission);
    void requireBoardModerator(Integer userId, Integer labelId);
}
```

实现建议：

- `hasPermission` 基于 `AccountRole` + 静态权限映射；
- `isSuperAdmin` 基于 `AccountRole.SUPER_ADMIN`，不再判断 id；
- `canModerateBoard`：
  - 超管返回 `true`；
  - 否则查询 `bbs_board_moderator` 是否存在 `user_id + label_id + status=1`；
- 权限不足抛出统一 `ForbiddenException`，由全局异常处理器转为 `ResultBean(403)`。

### 4.4 当前登录用户上下文

新增 `CurrentUserService`：

```java
public interface CurrentUserService {
    User getCurrentUser();
    Integer getCurrentUserId();
    boolean isSuperAdmin();
}
```

替换现有散落的：

- `SecurityContextHolder.getContext().getAuthentication()`；
- `getCurrentUserId()` 私有方法；
- 前端传入的 `operatorId` / `reviewerId` / `adminId`。

Controller 保留参数以兼容旧前端，但服务端必须**以登录态覆盖**；如果传入值与登录态不一致，返回“操作人身份校验失败”。

### 4.5 版主数据范围

`BoardModeratorService` 增加：

```java
boolean hasActiveRole(Integer userId, Integer labelId);
```

`appoint` 改造：

1. 校验目标用户、板块、操作人；
2. 校验累计积分 ≥ 300；
3. 查询同用户同板块记录：
   - 无记录：插入 `status=1`；
   - 有 `status=0` 记录：更新为 `status=1` 并刷新 `appoint_time`；
   - 有 `status=1` 记录：返回“该用户已是此版块版主”；
4. 不再依赖唯一键报错来处理重复任命。

板块级接口加校验：

- `pendingAdopts`：非超管只返回自己板块的数据；
- `approveAdopt`：非超管必须校验目标文章所属板块；
- `featured:recommend`：非超管必须校验文章所属板块；
- 文章删除/下架、违规处理等与板块相关的操作：按产品规则逐步加范围校验；
- 全局管理操作（用户管理、配置管理、版主任命）不做板块过滤。

### 4.6 自审批策略

新增 `SelfApprovalPolicy`：

```java
public interface SelfApprovalPolicy {
    void checkAdoptSuggestion(User operator, Article article);
    void checkReviewReport(User reviewer, Report report);
    void checkReviewAppeal(User reviewer, Appeal appeal);
    void checkReviewComplaint(User reviewer, ModeratorComplaint complaint);
    void checkReviewFeatured(User reviewer, FeaturedRecommendation recommendation);
    void checkSetFeatured(User operator, Article article);
}
```

实现中统一使用 `authorizationService.isSuperAdmin(operator)` 做豁免。原有“不能审批自己提问的最佳解答”保留全员限制。

### 4.7 登录响应与前端权限

登录成功后返回用户对象增加：

```json
{
  "id": 1,
  "username": "asiayak",
  "userType": "3",
  "role": "SUPER_ADMIN",
  "permissions": ["admin:access", "user:manage", "config:write"],
  "boardScopes": [
    { "labelId": 1, "roleType": "moderator" }
  ]
}
```

前端：

- `adminStore` 增加 `role`、`permissions`、`boardScopes`；
- 路由守卫改为检查 `to.meta.permission`，不再检查 `username === 'admin'`；
- `Sidebar` 菜单按权限点过滤；
- 新增 `v-permission` 指令或 `hasPermission()` 方法，用于按钮级隐藏；
- 无权限跳转 `/403`；
- 用户前台 `userStore.isModerator()` 修正或删除，避免继续使用错误判断。

### 4.8 数据模型与迁移

本次重构**原则上不新增权限表**。需要的数据变更：

1. 统一 `bbs_user.user_type`：
   - 空值更新为 `'1'`；
   - 确认 `id=1` 为 `'3'`；
   - 应用层枚举校验，避免写入非法值。
2. `bbs_board_moderator`：
   - 保留现有唯一键；
   - `appoint` 使用“更新旧记录”而不是重复插入；
   - 可选：增加 `update_time` 字段，便于审计；非必需。
3. 如需记录拒绝日志，可新增 `bbs_auth_denied_log`，但建议先使用应用日志，不阻塞主流程。

迁移文件必须遵守项目规范，同步更新：

- `init-mysql.sql`
- `init-pg.sql`
- `upgrade-mysql.sql`
- `upgrade-pg.sql`

每个迁移块使用 `-- @migration: vXXX-xxx`，并保证 MySQL / PostgreSQL 幂等。

### 4.9 错误码与审计

- 未登录：401，沿用 `RestAuthorizationEntryPoint`；
- 已登录但无权限：403，沿用 `RestfulAccessDeniedHandler`；
- 业务级权限失败：`ResultBean(403, "...")`，由全局异常处理统一转换；
- 拒绝日志建议记录：
  - 用户 ID、用户名；
  - 请求路径、HTTP 方法；
  - 所需权限/板块；
  - 结果与时间；
  - 不记录密码、Token、敏感内容。

## 7. 兼容与回滚

### 7.1 兼容策略

- 不删除现有接口路径；
- 登录响应只新增字段，不删除旧字段；
- `user_type` 继续使用字符串，避免前端大改；
- 旧 Token 仍可解析；权限每次请求实时计算，不把权限写进 JWT；
- 前端先发布“能识别新字段”的版本，再发布强制后端校验版本，降低风险。

### 7.2 回滚策略

- 代码回滚即可恢复旧行为；本次不涉及破坏性 DDL；
- 数据迁移仅做空值补齐和 `user_type` 修正，均可重复执行；
- 若新增拒绝日志表，可保留不影响业务；
- 若收紧“管理员创建管理员”导致业务阻塞，可通过配置开关临时放开，但需记录风险。

| ID | 决策点 | 建议默认值 | 影响 |

## 10. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 收紧 `/admin/**` 导致旧前端或脚本 403 | 业务中断 | 先梳理所有管理端调用；保留 `/admin/login` 兼容；灰度发布 |
| 普通管理员不能创建管理员 | 运维流程变化 | 提前确认 D3；必要时提供超管授权流程 |
| 版主板块范围扩大后误伤 | 版主无法处理跨板块内容 | 按 D4 分批上线；先列表、后动作 |
| `id=1` 改为角色判断后历史数据不一致 | 超管失效 | 迁移脚本统一 `id=1` 为 `user_type=3`；启动时校验 |
| 前端缓存旧权限 | 菜单/路由不一致 | 登录响应版本号；刷新时重新拉取；退出清理 sessionStorage |
| MySQL / PostgreSQL 迁移差异 | 部署失败 | 按项目规范四文件同步；CI 跑两种数据库 |
| 现有测试依赖旧行为 | 测试失败 | 更新测试预期；新增权限矩阵测试；不做无意义兼容 |

## 13. 结论

当前权限模型可以概括为：

> **账号角色（全局）+ 版主任职（板块范围）+ 硬编码超管豁免 + 前端展示控制**。

它不是菱形，也不是严格的树，而是“二维 + 策略”的混合模型。

建议按本规划分阶段重构，优先解决 P0 安全边界，再统一授权服务，最后同步前端权限。这样既能修复现有越权风险，又不会把项目拖入大规模重写。
