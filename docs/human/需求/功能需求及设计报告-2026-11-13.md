## 0. 结论速览

1. 本轮需求可以归为 **四条主线**：
   - **A. 排行榜与运营数据**：排行榜分类、组织人均排名、个人实际积分排名、年度运营周期、版主奖励可配置。
   - **B. 内容与互动**：帖子筛选排序、标签热榜、点赞/收藏/分享、匿名举报、可匿名标签、不计分标签、精华公示/展示、作者主页。
   - **C. 成长体系**：可配置等级（二维坐标 + 图标）、成就系统 + 燕尾旗勋章。
   - **D. 运营与治理**：组织自动导入、版主终审开关、发帖审核开关、待办提醒、月扣分提醒、权限按钮可见性。
2. **建议分四期实施**：P0 排行榜 + 权限修正 + 低成本配置项；P1 内容互动 + 标签策略；P2 等级/成就/主页/精华；P3 组织自动导入 + 提醒 + 年度周期。
3. 多数需求**不需要推翻现有架构**，但需要新增一批配置化表；其中 **组织自动导入、年度运营周期、成就规则引擎** 是三块工作量最大的设计。
4. **7 个关键口径已于 2026-11-13 拍板**（见 1.1 节）：分类允许重叠且“本部”沿用原逻辑、只排除测试账号、接受 24 级、匿名举报默认方案、保留原有获赞历史、年度周期只影响榜单、组织导入安全才自动执行。剩余实现细节见第 10 节。
5. 当前代码中有 3 个需要顺带修掉的隐患：
   - 收藏接口同时给文章“点赞数”和用户“获赞数”加 1，点赞/收藏语义混淆；
   - 删除评论/回复时无条件扣回积分，若该内容属于“不计分标签”，会误扣；
   - 管理员端“配置排名单位”按钮未做权限判断，版主点击会跳到系统管理页面。

## 2. 现状核实（代码证据）

### 2.1 排行榜：只有“全局排名开关”，没有分类，也没有人均

- `bbs_sa_org` 只有 `is_ranking_selected`（是否参与排名）一个全局开关（`SaOrg.java` 约 50 行）。
- 管理端在“组织管理”里逐个单位开关排名（`BBSUnitManage.vue` 约 108-117、494-520 行；`SaOrgController.batchUpdateRanking` 约 80-111 行）。
- 用户端排行榜 Tab **直接取组织树根节点的二级子节点**，没有“排行榜分类”概念（`bbs-ui/src/views/BBSPoints.vue` 约 356-374 行）。
- 组织榜按 **总分** 排序（`ArticleMapper.xml` 的 `pointsRank` 约 58-142 行；`ArticleServiceImpl.pointsRank` 约 761-826 行），没有 `memberCount`、`avgPoints`。
- 个人榜按积分日志 Top N（`ArticleMapper.xml` 的 `personalPointsRank` 约 145-193 行），方向是对的，但只返回前 N，且和“组织榜”是两套入口。

**结论**：排行榜分类、人均排名、总分/均分双展示、版主可见性都需要新增。

### 2.2 帖子浏览：只有关键词，没有分页/排序/多维筛选

- 用户端列表接口 `GET /common/article/getArticle?keywords=` 只接受关键词（`ArticleController` 约 283-287 行），服务层 `queryAllArticleList` 只按创建时间倒序，且**一次性返回全部**（`ArticleServiceImpl` 约 318-347 行）。
- 标签筛选是前端内存过滤：`filteredArticles()` 直接 `this.articles.filter(...)`（`BBSForum.vue` 约 267-270 行）。
- 热榜接口 `queryHot()` 只按浏览量取 10 条（`ArticleServiceImpl` 约 277-288 行），与标签无关。
- 文章实体没有“最后回复时间”“评论数/收藏数/分享数”等可排序字段；评论数由 `enrichWithCommentCounts` 临时补齐。

**结论**：需要新增列表查询接口、排序字段/索引，以及标签热榜接口。

### 2.3 点赞/收藏/分享：收藏与点赞语义混在一起

- 收藏表 `bbs_article_user` 实际承担“收藏”职责（`ArticleUser.java`）。
- 但 `ArticleUserServiceImpl.saveUserCollection` 在收藏成功后同时：
  - `articleService.articleGoodNumPlusOne(articleId)`（文章“获赞数”+1）；
  - `user.setGood(user.getGood() + 1)`（作者“获赞数”+1）。
- 代码中没有独立点赞表，也没有分享计数。
- 文章详情页没有点赞/收藏/分享操作区（`BBSArticleDetails.vue` 约 44-63 行只有举报和作者信息）。

**结论**：需要拆出“点赞”和“收藏”两张语义明确的表，修正历史口径；分享可只做前端复制链接 + 计数。

### 2.4 标签：没有匿名、没有不计分

- `ArticleLabel` 只有 `labelName`、`enabled`、`icon`、`description`、`labelType`（`ArticleLabel.java` 约 30-51 行），没有 `allow_anonymous`、`no_points`。
- 文章、评论、回复都没有 `is_anonymous` 字段。
- 发帖时标签是单选（`BBSArticleWrite.vue` 约 178-186 行），但没有任何匿名/计分策略。
- 积分逻辑分散在 `ArticleServiceImpl.publish`、`CommentServiceImpl`、`ReplyServiceImpl`、`ArticleUserServiceImpl`、`FeaturedRecommendationServiceImpl`、`CommentServiceImpl.checkHotBonus` 等处，没有统一的“该标签是否计分”入口。
- `CommentServiceImpl.deleteCommentById`（约 143-155 行）**无条件扣回 1 分**，不管这条评论当初有没有计分。

**结论**：需要标签策略字段 + 统一计分策略服务 + 删除时的“是否真实发过分”保护。

### 2.5 等级/成就：等级是硬编码除法，成就系统不存在

- `/user/level` 直接 `totalPoints / 100`（`UserController` 约 481-491 行），没有等级表、没有阶段/小阶段、没有图标。
- 没有成就/勋章相关表、Service、Controller、页面。
- 运营方案里的“每 100 积分一个等级”是硬编码，无法按领导要求做二维坐标配置。

**结论**：等级、图标、成就、勋章都是新建模块。

### 2.6 审核/精华：发帖自动通过，精华有终审但没有公示

- 发帖 `publish()` 直接 `article.setEnable(1)`（`ArticleServiceImpl` 约 164-181 行），没有前置审核；运营方案写的是“系统自动计分，管理人员定期抽查”，所以**当前实现与运营方案并不冲突**，但与领导口中的“发帖需要审核”不一致。
- 精华已有“版主推荐 → 管理员/总运营终审”链路（`FeaturedRecommendationServiceImpl.recommend/review`，约 90-208 行），终审要求 `featured:review`，版主只有 `featured:recommend`。
- 但管理员仍可通过 `/admin/featured/set` 直接设精华，绕过推荐；且没有“公示 5 个工作日”的字段和卡片。
- 终审通过给作者发通知时用了 `"adopt"` 类型（约 195 行），应为 `featured_granted`，会导致通知分类/文案不准确。

**结论**：需要“版主终审”开关、公示期、展示卡，并收紧直接设精华入口。

### 2.7 组织/运营：组织手工维护，导入只做“用户匹配”，奖励硬编码 15

- 组织只有手工新增/删除接口（`SaOrgController.addSaOrg/deleteSaOrgByOrgNo`，约 53-77 行）。
- `OrgImportService` 的职责是“从用户 Excel 里提取组织名称，到已有组织树里匹配”，**不会创建组织**，匹配不到就进 `unmatchedPairs`（`OrgImportService.java` 约 15-110 行）。
- 没有组织文件模板、文件校验、差异预览、批次、回滚。
- 版主月度奖励硬编码 `int rewardPoints = 15`（`BoardModeratorServiceImpl` 约 472 行），前端确认文案也写死“每人15积分”（`ModeratorPage.vue` 约 434 行）。
- 年度运营只依赖 `points-start-time` / `point-end-time` 两个字典，且只影响“累计排名”（`ArticleServiceImpl.pointsRank` 约 770-786 行），不影响等级、成就、奖励、热榜。

**结论**：组织自动导入、奖励配置、年度周期都需要补。

### 2.8 提醒/权限：有通知表，但没有管理端提醒中心；配置按钮无权限判断

- 已有 `bbs_notification`、通知分类注册表、未读汇总、前台 Header 红点（`NotificationCategory.java`、`BBSHeader.vue`）。
- 管理端没有通知铃铛/提醒中心，只有首页待办数字和侧栏红点。
- 没有“待办超过 X 分钟提醒/重复提醒/升级提醒”的规则表或定时任务。
- 管理端积分排名页“配置排名单位”按钮**没有权限判断**，直接 `$router.push('/unitManage')`（`BBSPoints.vue` 约 18 行）。版主有 `points:read`，但没有 `config:read`，点击后会进入系统管理，违背“业务管理 / 系统管理”边界。
- 权限模型：`config:read` / `config:write` 已是管理员默认、版主默认关闭（`Permission.java` 约 20-21 行），可复用为系统管理页面的权限点，避免新增枚举带来的存量权限组迁移问题。

### 2.9 作者信息/视觉：作者只是静态块，Hero 中间暗两边也暗

- 文章详情页作者信息是静态头像 + 昵称 + 单位（`BBSArticleDetails.vue` 约 53-62 行），没有悬浮卡、没有主页跳转。
- 用户端 `BBSUserinfo.vue` 是“我的设置”，不是“他人主页”；公开资料接口 `getUserinfoById` 还返回 `personnelId`（`UserController` 约 174-200 行），直接用于他人主页会泄露敏感信息。
- Hero 压暗层是“上下渐变 + 中心更暗的径向渐变”（`BBSForum.vue` 约 489-495 行），所以左右两侧也被压暗；领导觉得两侧看不清。

## 4. 总体设计

### 4.1 设计原则

1. **配置优先，不硬编码**：等级、成就、奖励、提醒、标签策略、热榜指标、组织导入映射都用表/字典配置；代码只保留安全兜底默认值。
2. **复用现有权限体系**：新系统管理页统一使用 `config:read`（查看）/`config:write`（修改），不新增权限枚举，避免存量权限组需要额外迁移。若后续需要更细粒度，再单独加 `ranking:manage` 等并写迁移。
3. **增量迁移、向后兼容**：所有新字段可空/有默认值；旧接口保留，新接口并行；旧 `is_ranking_selected` 不删除，只在前端隐藏。
4. **展示与实名分离**：匿名只影响展示层，数据库保留真实 `user_id`，便于风控、审计和追责。
5. **积分可追溯**：任何扣回必须先确认“当初确实发过分”，禁止无条件扣分。
6. **数据库双栈**：所有 DDL/DML 同步更新 `init-mysql.sql`、`init-pg.sql`、`upgrade-mysql.sql`、`upgrade-pg.sql`，迁移块幂等。

#### 4.3.1 新增系统管理页面

#### 4.4.2 管理端交互

- 左侧：组织树（可搜索、可展开），每个节点可拖拽；拖到右侧分类卡片即加入。
- 右侧：分类列表 + 详情；每个分类显示成员 chip、是否含下级、排序、启用状态。
- 拖入时弹小确认：“是否包含该单位下级组织？”默认“包含”。
- 支持从分类中移除、调整顺序、预览榜单。
- 保存时校验：同一分类内 `org_no` 不重复；根节点不允许删除；空分类允许但前台不显示。
- 组织树节点增加 `draggable="true"` 和 `dragstart` 事件（`OrgTree.vue` 现在只有点击/开关按钮），或新增一个 `mode="ranking-picker"` 的只读树。

#### 4.4.3 排名算法

对每个分类成员 `m`：

1. 计算成员组织集合：
   - `include_descendants=1`：`m.org_no` 及其全部后代；
   - `include_descendants=0`：仅 `m.org_no`。
2. `memberCount` = 这些组织下 `bbs_user.is_delete=0` 且 `is_test_account<>1` 的用户数（已拍板：只排除测试账号，不排除管理员/活跃用户）。
3. `totalPoints` = 这些用户在当前时间范围内 `bbs_points_log` 净积分之和（排除 `is_reversed=1`）。
4. `avgPoints` = `totalPoints / memberCount`，保留 2 位小数；`memberCount=0` 时记 0。
5. 排序：`avgPoints DESC, totalPoints DESC, org_no ASC`；并列时展示相同排名或顺序号（建议 `rank()` 同分同名次）。
6. 返回：`orgNo, orgName, totalPoints, avgPoints, memberCount, posts, replies, rankNum`。

实现建议：
- 在 Java 服务层聚合（先取组织子树、再批量查用户数/积分/发帖/回帖），避免 MySQL/PG 递归 SQL 差异；2000 用户规模足够。
- 查询加缓存 60 秒；分类配置变更时清缓存。
- 个人榜保持按积分日志净积分排序，返回 Top N + 当前用户排名卡。

#### 4.8.3 勋章形制（燕尾旗）

- 名称：燕尾旗式勋章 / 燕尾形勋章轮廓。
- 形制：矩形主体，底边中央倒 V 形切口，形成左右对称燕尾尖角；**一体化轮廓裁切**，禁止外挂两个三角形。
- 比例：尖角长度为主体高度 15%—20%；角度 30°—45°；左右对称；描边连续；24px 下清晰。
- 结构建议：
  - 外轮廓：燕尾旗；
  - 内圈：1px 内描边，距外轮廓 6–8px；
  - 中心：成就主题图形（星、齿轮、书、盾等）；
  - 顶部：绶带/挂环可选；
  - 颜色：每个成就一个主色，保持同一套明度/饱和度规则。
- 模板（`viewBox="0 0 256 256"`，示意）：

```svg
<svg viewBox="0 0 256 256" xmlns="http://www.w3.org/2000/svg">
  <path d="M44 36 H212 V214 L128 170 L44 214 Z"
        fill="#1f6f5c" stroke="#ffffff" stroke-width="6"
        stroke-linejoin="round"/>
  <path d="M60 52 H196 V196 L128 160 L60 196 Z"
        fill="none" stroke="#ffffff" stroke-opacity=".55" stroke-width="2"/>
  <!-- 中心图形放在 (128,112) 附近，安全区约 96×80 -->
</svg>
```

- 导入校验：
  - 仅允许 SVG/PNG；SVG ≤ 200KB，必须含 `viewBox`；
  - 禁止 `<script>`、`on*` 事件、`<foreignObject>`、外部 `href`/`url(http...)`；
  - 自动去掉 `width/height`，保留矢量；
  - 检查是否为空、是否超出画布、是否含位图；
  - 导入后可在 24/32/64px 预览。
- 模板下载：`GET /admin/achievement/medal/template` 返回带辅助线/安全区的 SVG。

### 4.9 提醒中心

#### 4.9.1 事件与默认规则

| 事件 | 目标权限 | 默认延迟 | 默认重复 | 说明 |
|------|----------|----------|----------|------|
| 待审核帖子 | `article:review` | 10 分钟 | 60 分钟 | 仅开启前置审核时 |
| 待审核举报 | `report:review` | 10 分钟 | 60 分钟 | 按板块 |
| 待审核申诉 | `appeal:review` | 30 分钟 | 120 分钟 | 按板块 |
| 精华待终审 | `featured:review` | 30 分钟 | 120 分钟 | 版主终审开启后改为 `featured:recommend` |

| 月扣分提醒 | 用户本人 | 0 | 每月一次 | 不走待办规则 |

#### 4.9.2 机制

- 定时任务每 5 分钟扫描待办表，按规则判断“超时未处理”。

- 提醒内容聚合：同一用户同一规则多条待办合并为“您有 N 条待处理举报”，避免刷屏。
- 升级：超过 `escalate_minutes` 仍未处理，给更高权限（如管理员/超管）发一次升级提醒。
- 管理端 Header 增加铃铛：未读数、下拉最近提醒、跳提醒中心；提醒中心页支持已读/全部已读/按规则筛选。
- 配置页：规则列表、开关、权限、范围、延迟、重复、每日上限、免打扰、升级、测试发送、预览收件人。

### 4.10 组织自动导入

#### 4.10.1 目标

- 组织部每年更新组织文件时，不再手工点“新增/删除”。
- 新文件能自动检测是否满足导入要求；不满足时**不入库**，给出明确错误。
- 格式变化时通过“映射配置”适配，而不是改代码。
- 破坏性变更（删除、移动有用户的组织）必须人工确认。

#### 4.10.2 流程

```
文件投放（目录/上传/API）
  → 计算 hash，查重
  → 选择映射模板（或按表头自动识别）
  → 解析 + 结构校验
  → 与数据库 diff（新增/改名/移动/停用/无变化）
  → 生成 staging 批次 + 预览
  → 安全项自动应用 / 破坏项等待确认
  → 事务写入 + 记录 before/after
  → 通知结果；失败文件移入 failed/ 并附错误 JSON
  → 支持按批次回滚
```

#### 4.10.3 校验规则（必须全部通过才允许应用）

- 表头：必填列存在；支持别名映射；未知列给出警告。
- 数据：`org_no` 非空、唯一、长度/格式符合；`org_name` 非空、≤255；`p_org_no` 在文件或库中存在。
- 结构：不能有环；根节点唯一；不能把根节点挂到别的节点下；`org_tree` 必须与父子关系一致。
- 业务：
  - 不能删除仍有用户的组织（需先迁移用户）；
  - 不能把组织移动到自己的子孙下；
  - 批量停用/移动超过阈值（如 10%）需二次确认；
  - 同名但 `org_no` 不同视为新增；同 `org_no` 改名视为重命名。
- 文件：hash 重复则提示“该文件已导入”；空文件、超大文件、非 Excel/CSV 直接拒绝。
- 失败：整批回滚，不写 `bbs_sa_org`；错误定位到行/列。

#### 4.10.4 自动导入接口

- `POST /admin/org/import/validate`：上传文件，返回批次 ID + 校验结果。
- `POST /admin/org/import/apply`：应用指定批次；`mode=SAFE` 只应用新增/改名，`mode=FULL` 应用全部（需 `confirm=true`）。
- `GET /admin/org/import/batches`、`GET /admin/org/import/batch/{id}`、`POST /admin/org/import/rollback/{id}`。
- `GET /admin/org/import/template`：下载模板。
- 自动扫描：配置 `org_import_dir`、`org_import_cron`、`org_import_auto_apply`（默认 `SAFE`），定时扫描新文件；也可由外部系统调用 `POST /admin/org/import/auto`（需管理员 token 或内网白名单）。
- **自动执行规则（已拍板）**：整批校验后，如果全部是“新增/改名”等安全变更，自动应用；只要出现任一不安全项（删除、移动、影响已有用户、批量变更超阈值），**整批停止、不写入任何数据**，生成站内提醒并保留错误批次，等待管理员确认后手动应用。不做“安全项先应用、危险项后确认”的部分执行。
- 所有导入/回滚写审计日志。

### 4.11 年度运营周期

#### 4.11.1 现状问题

- 现在只有 `points-start-time` / `point-end-time` 控制“累计排名”的时间范围；
- 等级按终身总积分；
- 成就、奖励、热榜、精华规则都没有周期概念；
- 每年换方案时需要手工改多个字典，容易漏。

#### 4.11.2 设计

- 新增“运营周期”管理页：

  - 归档：只读，保留快照。
- 周期配置覆盖：
  - `bbs_cycle_config` 存该周期的字典覆盖值（如发帖分、回帖分、精华分、奖励分、热榜默认指标、等级 profile）；
  - 读取顺序：ACTIVE 周期覆盖 → 全局字典 → 代码默认值。
- 积分：
  - `bbs_points_log.cycle_id` 写入当前周期；
  - 历史数据按 `create_time` 回填到对应周期；
  - **榜单查询按 `cycle_id` 过滤；总积分不重置，等级继续按终身累计计算**（已拍板）。
- 等级：
  - `bbs_level_profile.cycle_id` 可空；为空表示全局；
  - 本期固定 `level_points_scope=LIFETIME`，不提供“年度清零”切换；年度周期只影响榜单、奖励和周期配置。
- 成就：
  - `bbs_achievement.cycle_id` 可空；为空表示长期成就；
  - 年度成就可每年复制一份，避免历史混淆。
- 归档：
  - 周期结束时生成 `bbs_ranking_snapshot` 和周期汇总（总积分、发帖、回帖、精华、活跃人数），供年度评优。

### 4.12 精华公示/展示与审核

#### 4.12.1 流程

```
版主推荐（pending）
  ├─ 管理员终审（默认）──┐
  └─ 版主终审（开关开启）─┤
                          ↓
                    公示中（publicizing，默认 5 个工作日）
                          ↓ 公示期满无异议
                    已发布（published，文章 is_featured=1）
                          ↓ 管理员可撤销
                    已撤销（revoked）
```

- `featured_final_review_mode=ADMIN_FINAL`：现状，`featured:review` 才能终审。
- `featured_final_review_mode=MODERATOR_FINAL`：有 `featured:recommend` 且是该板块版主的用户可直接终审；仍要过自审批策略（不能审自己的推荐）。
- 公示期从终审通过开始计算；默认 5 个工作日（跳过周末，节假日可配置）。
- 公示期内文章可以标记“公示中”，但**是否立即计入精华积分**需拍板：
  - 推荐：终审通过即发精华积分（保持现状），公示期只影响“展示/是否可撤销”；
  - 或公示期满才发分（更严谨，但用户体验慢）。
- 公示期异议：复用举报入口，举报目标为文章，原因加“精华公示异议”；管理员核实后可撤销精华。若后续需要独立异议表，再加 `bbs_featured_objection`。
- 直接设精华 `/admin/featured/set`：建议限制为超管应急入口，必须填理由并写审计；普通管理员走推荐流程。

#### 4.12.2 卡片

- `FeaturedShowcaseCard`（展示卡）：
  - 大封面（16:9）、精华徽章、标题（2 行）、摘要（2 行）、作者 badge、单位、发布时间、浏览/评论/点赞/收藏、标签；
  - 首页中部 1 张 + 侧栏 2–3 张小卡；精华页网格展示。
- `FeaturedNoticeCard`（公示卡）：
  - “精华公示”标识、文章标题、推荐理由、推荐人/版主、公示起止、剩余天数、当前状态；
  - “查看帖子”“我要反馈”；
  - 公示结束后自动从公示区移除。
- 配置：`featured_public_enabled`、`featured_public_days=5`、`featured_showcase_count=3`。
- 修复通知类型：终审通过给作者发 `featured_granted`，不要用 `adopt`。

### 4.13 作者悬浮卡与公开主页

#### 4.13.1 悬浮卡

- 文章列表作者、详情页作者、评论区作者统一使用 `BBSUserBadge` + `BBSUserHoverCard`。

#### 4.14.3 三个低成本配置项的实现口径

**（1）每日浏览 1 分钟**

- `LoginLogServiceImpl` 的代码缺省值从 `10` 改为 `1`，`init-*.sql` 的种子值改为 `1`。
- 迁移只更新“仍为默认 10”的环境：`UPDATE bbs_dict SET dict_value='1' WHERE dict_key='login_browse_minutes' AND dict_value='10'`；生产已配置为 1 的不受影响。
- 前端所有“满 10 分钟”的文案改为读取配置或使用“满 1 分钟”动态文案。

**（2）版主月度奖励 400**

- 新增字典 `moderator_reward_points=400`；`BoardModeratorServiceImpl.doMonthlyReward` 从字典读取，缺省 400。
- 手动发放确认文案、通知文案、Controller Swagger 描述、Service 注释全部改为动态值，不再出现“15 积分”。
- 自动发放任务、手动发放、取消/恢复逻辑共用同一个 `rewardPoints`，避免两套口径。

**（3）月累计扣分 ≥10 提醒**

- 在 `PointsLogService.adjustUserPoints` 的负数记录落库后触发检查；另设每日补偿任务，防止历史漏提醒。
- 统计口径：当前自然月内、未被撤销的负积分之和的绝对值；`is_reversed=1` 的记录不计入。
- 达到阈值且 `bbs_points_alert` 中无 `(user_id, 'MONTHLY_DEDUCTION', yyyy-MM, 10)` 记录时：
  - 写 alert 去重；
  - 发 `monthly_deduction_alert` 站内通知：“您本月累计扣分已达 X 分，请注意内容规范，可在‘我的违规/积分明细’查看详情。”
- 撤销扣分不回撤已发提醒；下月重新计算。阈值、开关均来自配置。

## 6. 关键流程

### 6.1 精华审批与公示

```
版主推荐
  │
  ├─ featured_final_review_mode=ADMIN_FINAL
  │     └─ 管理员/总运营终审（featured:review）
  │
  └─ featured_final_review_mode=MODERATOR_FINAL
        └─ 版主终审（featured:recommend + 板块范围）
              │
              ▼
        公示中（publicizing）── 公示卡展示
              │  5 个工作日
              ├─ 有异议 → 管理员核实 → 撤销/维持
              ▼
        已发布（published）── 展示卡/精华页
```

### 6.2 组织导入

```
新文件 → hash 查重 → 映射模板 → 解析
  → 结构校验（列/唯一/父子/环）
  → 业务校验（用户/移动/停用/阈值）
  → diff 预览
  → SAFE：新增/改名自动应用
  → FULL：人工确认后应用
  → 写 before/after + 审计
  → 失败：整批回滚 + 错误文件归档
```

### 6.3 成就评估

```
行为事件 → 异步事件总线 → 计算指标 → 匹配规则
  → 满足且未解锁 → 写 bbs_user_achievement → 通知
  → 不满足 → 更新 progress
每日凌晨全量重算兜底
```

## 7. 实施计划

### 7.1 分期

| 阶段 | 范围 | 主要交付 | 依赖 | 估算 |
|------|------|----------|------|------|
| P0 | 排行榜分类/人均、权限可见性、Hero、奖励 400、浏览 1 分钟、月扣分提醒 | 表 + 接口 + 管理端排名页 + 用户端榜单 + 配置 | 无 | 6–8 人日 |
| P1 | 帖子筛选排序、标签热榜、点赞/收藏/分享、匿名举报、标签匿名/不计分 | 内容接口 + 详情页互动 + 标签管理 + 积分策略 | P0 的权限/配置基础 | 8–10 人日 |
| P2 | 等级 + 图标、成就 + 勋章、作者悬浮卡/主页、精华公示/展示、版主终审开关 | 等级/成就管理页 + 勋章模板 + 主页 + 精华卡 | P1 的内容/标签 | 10–12 人日 |
| P3 | 组织自动导入、提醒中心、年度运营周期 | 导入批次/校验/回滚 + 提醒规则/任务 + 周期管理 | P0/P2 的配置与权限 | 10–14 人日 |

> 合计约 **34–44 人日**（不含视觉精修、生产数据清洗、等保/安全评审）。一名全栈约 7–9 周；两名并行约 4–5 周。估算为设计阶段粗估，开发前需按接口/页面拆分复核。

### 7.2 建议顺序

1. **先做 P0**：排行榜和权限修正是领导最直接感知的，且能验证“排名管理 + 组织树拖拽”这条新交互。
2. **再做 P1**：内容互动和标签策略会碰积分，先把“计分/扣回”统一，后面等级/成就才不会被旧逻辑污染。
3. **P2**：等级/成就依赖 P1 的积分与标签；精华公示依赖 P1 的展示卡样式。
4. **P3**：组织导入和年度周期是“运营基础设施”，不阻塞日常功能；提醒中心可先上线基础版（站内铃铛 + 超时提醒），再补升级/免打扰。

### 7.3 每阶段完成定义（DoD）

- 4 个 SQL 文件同步，MySQL/PG 迁移/回滚/再迁移通过；
- 后端单测 + 接口测试通过；
- 两个前端 `npm run build` 通过；
- 权限矩阵回归：版主看不到系统管理入口，直接访问 403；
- 关键页面 Playwright/手工验收；
- CHANGELOG 更新（按项目规范）；
- 不擅自提交 git，待确认后分仓提交。

- 组织榜（约 2000 用户、数十组织）单次查询 < 1s，缓存后 < 200ms。
- 帖子列表分页 < 500ms（有索引）。
- 热榜 < 300ms（缓存）。
- 成就全量重算 2000 用户 < 5 分钟（异步，可分批）。
- 组织导入 1 万行 < 30 秒（不含人工确认）。

### 8.3 迁移验证

- 新库：`init-mysql.sql` / `init-pg.sql` 全量建表 + 种子数据，启动无报错。
- 旧库：`upgrade-*` 幂等执行；重复启动不重复插入；回滚脚本可用。
- 数据回填：
  - `last_reply_time`、`comment_num`、`favorite_num`；
  - `bbs_article_user` 去重后加唯一键；
  - 分类/等级/成就种子；
  - `points_log.cycle_id`（若启用周期）。
- 迁移前后对比：组织数、用户数、文章数、积分总额不变。

## 9. 风险与回滚

| 风险 | 影响 | 应对 |
|------|------|------|
| 排行榜分类口径不清 | 榜单结果与领导预期不符 | 先做 5 个默认分类 + 预览；允许重叠；上线前用生产数据核对 |
| 人均分母争议 | 人少单位排名异常 | 已拍板只排除测试账号；测试账号在用户管理勾选；页面显示人数，便于解释 |
| 匿名被滥用 | 攻击、违规内容追责难 | 保留 `user_id`；超管可核查；审计；匿名不适用于管理人员？可配置 |
| 不计分标签误扣 | 用户积分被错误扣减 | 扣回前查加分日志；先修 `deleteCommentById`；补单测 |
| 点赞/收藏历史数据混淆 | 旧“获赞数”失真 | 已拍板保留旧值作为历史热度；新增点赞继续累加，收藏不再增加点赞/获赞；页面文案明确“点赞/收藏” |
| 成就规则太复杂 | 管理端难用、性能差 | 首批只做单层 AND/OR；嵌套用高级 JSON；每日全量兜底 |
| SVG 勋章恶意内容 | XSS/外链 | 白名单解析、禁脚本/外链、大小限制、服务端清洗 |
| 组织导入误删/误移 | 组织架构和用户归属混乱 | 全批校验；全安全才自动执行；任一不安全项整批停止并提醒；批次回滚；导入前备份 |
| 年度周期切换 | 历史榜单/积分不可追溯 | `cycle_id` + 快照 + 归档只读；切换前备份 |
| 新权限枚举未授予存量组 | 管理员看不到新菜单 | 本轮复用 `config:read/write`；若新增枚举，必须写迁移补权限 |
| 提醒刷屏 | 管理员反感 | 聚合、去重、每日上限、免打扰、升级；先小范围开启 |
| 版主终审放权 | 精华质量下降 | 默认关闭；开启后保留公示/撤销/审计；可随时切回 |

### 回滚策略

- 代码：按阶段独立开关，出问题先关配置（如 `featured_public_enabled=0`、`article_publish_mode=AUTO`、`featured_final_review_mode=ADMIN_FINAL`）。
- 数据：
  - 新表可保留，不回滚 DDL；
  - 新增列可保留，旧代码忽略；
  - 组织导入按批次回滚；
  - 周期切换回上一个 ACTIVE，保留新周期为 DRAFT/ARCHIVED。
- 迁移：每个 `@migration` 块幂等；上线前在 MySQL/PG 各跑一次“迁移→回滚→再迁移”。

### 10.2 仍需在实现/部署前确认的细节

1. **匿名内容对版主是否可见真实作者**：默认列表脱敏、超管可核查；若版主需要直接看到实名，需调整脱敏策略。
2. **发帖审核是否开启**：默认保持 `AUTO`；若要开启前置审核，需确认审核时效和版主范围。

4. **精华直接设置**：默认保留超管应急入口，普通管理员走推荐流程；需确认是否保留。
5. **提醒渠道**：默认只做站内；邮件/短信/企业微信需另行确认。
6. **测试账号是否完全从个人榜隐藏**：默认是（个人榜、组织榜、人均都不出现）；若只想从组织人均分母排除，需调整。
7. **年度周期上线时间**：属于 P3，可先用现有 `points-start-time`/`point-end-time` 过渡。
8. **标签匿名/不计分历史追溯**：默认只影响新内容，不追溯历史。
