## 二、现状核实（代码证据）

### 2.1 账号级限制（需求 1 相关）

- 字段：`bbs_user.post_restricted`（0/1）+ `post_restricted_until`（截止时间，字符串）。
- 触发入口 `ViolationServiceImpl.addViolation`（约 147–185 行）：
  - `leak` 类型 → 立即 `post_restricted=1`，**永久限制**（`until=null`，LambdaUpdateWrapper 强制置空）；
  - 其他类型 → 月度累计扣分 > 20 分自动限制发帖 **7 天**（`until = 当前+7天`）。
- 解除入口：`UserController` 已有"管理员限制/解除用户发帖"接口（restricted=0 即解除），且查询时若 `until` 已过期会自动解除（约 480–485 行）。
- **缺口**：`ViolationServiceImpl.doCancel`（取消违规，约 444–471 行）只回滚积分 + 恢复内容可见性，**不解除 `post_restricted`**。即：误判违规被取消后，用户发帖权限仍是受限的（C 批 #14 实施记录中也已注明"leak/月度限制属账号级状态，本次不解除，留待后续单独设计"）。

### 2.2 自操作权限（需求 2 相关）

| 操作 | 接口 / 方法 | 现状 | 缺口 |
|------|-------------|------|------|
| 采纳建议 | `POST /admin/suggestion/adopt`（`ArticleController.adoptSuggestion`，约 535–581 行） | 已有"不能采纳自己的建议"（`operatorId.equals(article.getUserId())` 拒绝），**超管同样被拒绝** | ① `operatorId` 来自前端传参，**无登录态身份校验**（可伪造他人 id 绕过自采纳拦截，D 批未覆盖此接口）；② 超管不豁免 |
| 举报审批 | `ReportServiceImpl.reviewReport`（约 195–230 行） | 已有"举报人不得审核自己的举报"（#2 安全修复），但**超管与普通管理员一视同仁**均被拒绝 | 需求要求超管豁免 |
| 申诉审批 | `AppealServiceImpl.reviewAppeal`（约 91–133 行） | 有登录态身份校验（防伪造），**无"审核人不得审核自己的申诉"**（`appeal.userId == 审核人` 未拦截） | 需新增自审拦截 |
| 精华推荐审批 | `FeaturedRecommendationServiceImpl.review`（约 104–165 行） | 有登录态身份校验，**无"审核人不得审核自己的推荐"**（`rec.recommenderId == 审核人` 未拦截） | 需新增自审拦截 |
| 版主投诉审批 | `ModeratorComplaintServiceImpl.review`（约 94–138 行） | 有登录态身份校验，**无"审核人不得审核自己的投诉"**（`complaint.reporterId == 审核人` 未拦截） | 需新增自审拦截 |
| 设为精华 | `POST /admin/featured/set` → `ArticleServiceImpl.setFeatured`（约 913–968 行） | 无"不得对自己的帖子设为精华"校验；操作人仅从 JWT 登录态取（用于通知） | 需新增自设拦截 |

- 超级管理员判定：`ConstantUtil.SUPER_ADMIN_ID = 1`（系统内置超管，初始化 SQL 约定，勿改动态）。
- 前端现状：`ArticlePage.vue` 采纳建议按钮无作者判断（后端拦截兜底）、传 `operatorId=getAdminId()`（sessionStorage 兜底 1）；设为精华按钮无作者判断；`ViolationPage.vue` 取消违规弹窗文案未提及"解除发帖限制"。

## 三、方案设计

### 3.1 需求 1：取消违规同时解除账号级限制

**改动点**：`ViolationServiceImpl`（`doCancel` + 通知）。

1. **解除发帖限制**：`doCancel` 中回滚积分、恢复内容之后，追加解除该违规用户的发帖限制：
   ```java
   // 取消违规 → 解除账号级发帖限制（LambdaUpdateWrapper 强制置空 null 字段）
   userService.update(user, new LambdaUpdateWrapper<User>()
       .eq(User::getId, v.getUserId())
       .set(User::getPostRestricted, 0)
       .set(User::getPostRestrictedUntil, null));
   ```
2. **通知用户**：追加一条 `post_restricted` 类型通知："您的发帖限制已随违规取消一并解除"（fromUser=操作人）。
3. **成功文案**：`cancelViolation` 返回值与 `ViolationPage.vue` 的 `successMsg` 更新为"违规已取消，扣分已回滚，关联内容与发帖限制已恢复"。
4. **口径（推荐）**：解除前检查该用户是否仍存在其他 `active` 违规；若存在且仍满足触发条件（leak 类型 / 其他违规月度累计仍 >20），**保留限制**并在返回信息中说明"仍存在其他违规，发帖限制未解除"。若用户要求无条件解除（罗哥原意"同时解除"），则简化为此逻辑删除该检查——**待确认**（见第六节）。

**可复用工具（需求 1 第二句）—— 默认方案**：

用户原话"让 AI 尝试开发可复用工具快速恢复关联操作项目"，按最贴合项目现状的理解，设计为**后端可复用恢复组件 + 一处复用入口**：

1. **抽取通用恢复服务** `ViolationRecoveryService`（或直接在现有 `ViolationServiceImpl` 内把 `doCancel` 的回滚核心提炼为公共方法 `recoverViolation(violation, operatorId)`），统一包含：回滚积分日志 → 恢复内容可见性 → 解除发帖限制 → 状态置 cancelled 留痕 → 通知。
2. **复用点**：`cancelViolation`（管理端取消违规）与 `autoCancelByAppeal`（申诉通过自动取消）两处共用同一恢复逻辑，消除重复。
3. **可选增强（待确认）**：新增一个管理端"快速恢复"入口（如 `POST /admin/violation/recover` 支持按 userId 或 violationId 批量恢复），供误判后的批量快速处置；或提供运维 SQL/脚本模板（仅查询 + 幂等 UPDATE，不碰 schema）。

### 3.2 需求 2：除超级管理员外，不得自采纳 / 自审批 / 自设精华

统一模式：所有校验以 **JWT 登录态身份**为准（沿用 D 批 `getCurrentUserId()` 模式），超管（`id == ConstantUtil.SUPER_ADMIN_ID`）豁免。逐项改动：

| 项 | 文件 | 改动 |
|----|------|------|
| 2.1 采纳建议 | `ArticleController.adoptSuggestion` | ① 取登录态 `currentUserId`，未登录报错；前端传入 `operatorId` 与登录态不一致报"操作人身份校验失败"；校验后**以登录态覆盖**。② 自采纳校验改条件：`!isSuperAdmin && operatorId.equals(article.getUserId())` → 拒绝（超管可采纳自己的建议） |
| 2.2 举报审批 | `ReportServiceImpl.reviewReport`（含批量路径） | 自审拦截改条件：`!isSuperAdmin && reporterId.equals(reviewerId)` → 拒绝。**保留**"举报人即审核人，不予计分"的防刷分保护（超管自审自己的举报仍不计奖励分——待拍板，见第六节） |
| 2.3 申诉审批 | `AppealServiceImpl.reviewAppeal` | 登录态校验之后新增：`!isSuperAdmin && appeal.getUserId().equals(currentUserId)` → 拒绝"不能审核自己的申诉" |
| 2.4 精华推荐审批 | `FeaturedRecommendationServiceImpl.review` | 新增：`!isSuperAdmin && rec.getRecommenderId().equals(currentUserId)` → 拒绝"不能审核自己的推荐" |
| 2.5 版主投诉审批 | `ModeratorComplaintServiceImpl.review` | 新增：`!isSuperAdmin && complaint.getReporterId().equals(currentUserId)` → 拒绝"不能审核自己的投诉" |
| 2.6 设为精华 | `ArticleServiceImpl.setFeatured` | 在"设为精华"（`isFeatured==1`）分支新增：`!isSuperAdmin && article.getUserId().equals(operatorId)` → 拒绝"不能将自己的帖子设为精华"；**取消精华不受限**（便于管理员纠错） |

- 超管判定统一封装：`isSuperAdmin(Integer userId)`（`userId != null && userId == ConstantUtil.SUPER_ADMIN_ID`），或各 Service 内联判断，与现有 `ReplyController` 超管判定风格一致。
- **前端（可选，体验层）**：`ArticlePage.vue` 采纳建议 / 设为精华按钮对"当前管理员 == 文章作者 且非超管"时隐藏或置灰，提示文案与后端一致；`ViolationPage.vue` 取消违规成功文案同步更新。后端校验为安全边界，前端不做也不影响安全。

## 六、待确认点（拍板后开工）

1. **可复用工具的形态**（需求 1）：默认方案 = 抽取统一恢复服务供取消违规/申诉通过复用；是否需要额外的"按 userId/violationId 批量快速恢复"管理端入口或运维脚本？
2. **解除限制的口径**（需求 1）：取消违规时若该用户**仍存在其他 active 违规**且限制条件仍成立，是"保留限制 + 提示"（推荐，更严谨）还是"无条件解除"（字面按罗哥原意）？
3. **超管自审举报计分**（需求 2）：超管豁免自审拦截后，其审核自己举报的 +2 奖励分是否照常发放？（推荐：保留"举报人即审核人不予计分"防刷分，超管也不发）
4. **前端按钮**：管理端按钮是否需要随规则同步隐藏/置灰（推荐做，体验更一致），还是仅后端拦截？
