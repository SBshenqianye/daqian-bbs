# 任务：为当前项目落地一套「可验收、可回滚、可离线」的自动化部署

你是这个项目的交付工程师。目标不是写出"能跑一次"的脚本，而是让**下一个人在不问你任何问题的情况下**完成：构建 → 打包 → 部署 → 验证 → 回滚。
下面这套做法来自一个真实的全栈项目（Spring Boot + 两个 Vue 前端 + PostgreSQL + podman 离线内网），请按你项目的实际情况裁剪，但**原则和判据不要删**。

---

## 0. 先摸清现状，再动手

在写任何脚本之前，先输出一份现状清单（不知道的标"未知"，不要猜）：

| 项 | 需要确认的内容 |
| --- | --- |
| 构建机 | 操作系统 / 有无 WSL / 是否联网 / 内存多大 |
| 运行机 | 操作系统 / 容器运行时（docker / podman / 裸进程）/ 是否离线内网 |
| 构建命令 | 前端、后端、依赖安装，一条一条写全（含必须串行的地方） |
| 产物路径 | 每个产物的路径、体积、是否可增量 |
| 运行方式 | 进程或容器 / 端口 / 反向代理 / 健康检查 URL |
| 配置 | 环境变量文件位置、哪些是密钥、哪些有默认值 |
| 数据库 | 类型 / 迁移机制 / 迁移记录表 / 初始化脚本是否会 DROP |
| 现有部署 | 手工步骤、历史事故、出事时谁知道怎么回滚 |

**关键判断**：只有"构建机 ≠ 运行机"或"运行机离线"时，才需要打包分发。同机部署别硬加离线包，会白造一套维护负担。

## 1. 八条硬原则（违反任何一条都算没做完）

1. **单一入口**：一个人只需要记一条命令。`./deploy.sh` 默认按目录特征自动识别"开发机 / 生产机"，不用记参数；`-n/--dry-run` 只打印计划。
2. **四段分离**：构建（build）/ 打包（package）/ 部署（deploy）/ 验证（verify）各自独立可跑。任何一段失败，前面已完成的产物仍可复用。
3. **判据必须能变红**：每个"验证"都要能被故意改坏而失败。写完自检后，手动注入一次错误（改错 URL、改错断言、回滚一行代码），确认它 exit 1，再还原。绿不起来的检查等于没写。
4. **产物取证，不要源码自证**：版本号、迁移版本、依赖清单一律**从最终产物里读**（jar 内的 SQL / 包内 version.txt），再和源码比对。只比源码等于自己给自己盖章。
5. **可回滚**：每次部署生成 `versions/<时间戳>/`，`latest` 是软链；回滚 = 改软链 + 重启，一条命令，不需要重新构建。
6. **幂等**：脚本重复执行结果一致。重复 `mkdir -p`、`ln -snf`、`rm -f` 后再 `run`；不要依赖"目录还不存在"这种前提。
7. **失败保留现场**：验证不通过就**不归档、不删包**，把包留在原地，并打印回滚命令和日志位置。成功才归档。
8. **不碰生产数据**：`init-*.sql`、`DROP`、`TRUNCATE`、对生产库的写入，一律先停下来问人。

## 2. 目录与脚本骨架

按"**会不会碰生产**"分层，而不是按技术栈分层：

```
scripts/
├── lib/            # 公共函数：日志、进度、runner 探测
├── dev/            # 只动本机：up / down / restart / verify / package / negative-smoke
├── prod/           # 产出发布物，或直接在服务器执行：
│   ├── base.sh          # 基础镜像构建/导出/加载（依赖下沉时才需要）
│   ├── package.sh       # 打升级包（含 sha256、version.txt）
│   ├── verify-build.sh  # 构建机自检：产物是否合格
│   ├── offline.sh       # 服务器端：首次安装 / 升级 / 修复
│   ├── one-key-deploy.sh# 一键：打包→验证→部署→再验证→归档
│   └── verify-server.sh # 运行机自检：部署结果是否合格
├── test/           # 验收工具，不参与发布物
└── SCRIPT.md       # 唯一说明书：每个脚本的用法、退出码、判据
deploy.sh           # 根目录薄壳，只做转发
```

每个脚本头部必须写：用途、前置条件、用法示例、退出码含义。`SCRIPT.md` 里按脚本列同样内容，别让文档和脚本两头维护两份事实。

## 3. 分阶段实施（每阶段都能独立验收，不要一次全上）

**P0 最小可用（半天）**
- `dev/up|down|restart`：按**端口**杀进程树，不杀全部 node/java；日志落到固定目录。
- `dev/verify`：串行构建 + 启动 + 冒烟，一条命令给出通过/失败。
- 判据：停掉服务后 `verify` 必须红；起服务后必须绿。

**P1 可分发（1–2 天）**
- `package.sh`：只打包**已存在的产物**，缺产物要警告并让人确认，不偷偷重新构建。
- `version.txt`：`build_time` / `schema_version`（从包内后端产物里读）/ `git_commit`。
- 同名 `.sha256`（统一大写，方便 `sha256sum -c` 和手工比对）。
- `verify-build.sh`：包体积上限、包内关键文件齐全、包内版本 == 源码版本。
- 判据：故意用旧产物打包，`verify-build.sh` 必须报 FAIL。

**P2 可部署可回滚（2–3 天）**
- `offline.sh`：`--install` / `--upgrade <tar>` / `--repair`，自动识别包类型，解压到临时目录并在退出时清理。
- 升级用版本目录 + `latest` 软链；容器用**重建**而不是 `restart`（restart 不会换镜像）。
- 启动即探针：见 §5。
- 判据：连续升级两次，`versions/` 下有两个目录、软链指向最新、旧版本可直接回滚。

**P3 一键化（1 天）**
- `one-key-deploy.sh`：预检 → 打包 → 产物验证 → 部署 → 运行验证 → 归档，任何一步失败立即中止并打印回滚命令。
- 生产模式：3 秒倒计时（仅 TTY）、`-y` 免确认；成功才把包移入 `archive/`。
- 判据：`-n` 的预检能报出"产物早于源码""缺少某产物""sha256 不匹配"。

## 4. 预检（preflight）是性价比最高的一段

部署脚本前 30 行决定它会不会半夜出事。至少检查：

- 必需命令是否存在：`curl`、`tar`、`sha256sum`、`python3`、容器运行时。
- 构建产物是否齐全（缺就**直接失败**，不要"警告后继续"）。
- **产物是否早于源码**：`find src -newer <产物>` 有输出就提示"可能忘了重新打包"，交互确认。
- 打印 `git rev-parse --short HEAD`、分支、未提交文件数。
- 生产：打印 `latest` 当前指向、是否首次部署；有 `.sha256` 就核对，不匹配立即中止。
- 同目录依赖是否同步到服务器（例如服务器上也需要 `offline.sh`、`verify-server.sh`），缺了在部署前报，不要部署到一半才 404。

## 5. 部署即自检：三类探针，缺一不可

1. **完整性**：`sha256` 校验；包内 `version.txt` 与源码最新迁移号一致。
2. **挂载探针**：宿主目录写一个探针文件 → 进容器 `cat` 读回。读不到 = 绑定挂载静默失效（老 podman 在 SELinux 下真会这样），此时上传会写进容器可写层，表现为"上传成功、图片全 404"。
3. **端到端回读**：宿主写一张 1×1 PNG → 走 nginx `GET /files/...`，必须 200。只验挂载不够，文件服务和路由也可能坏。

三类都通过只代表"部署正确"，**不代表业务正确**，仍需一次浏览器回归（发帖 / 上传 / 登录）。

## 6. 升级包约定

```
bbs-upgrade-<YYYYMMDD_HHMMSS>.tar.gz
bbs-upgrade-<...>.tar.gz.sha256
└── upgrade-<时间戳>/
    ├── upgrade.sh        # 生成时就把时间戳写死，服务器端零参数
    ├── version.txt       # build_time / schema_version / git_commit
    ├── <后端产物>
    └── <前端 dist>
```

- `upgrade.sh` 逻辑固定：建版本目录 → 拷产物 → `ln -snf` 切 `latest` → 重建/重启容器 → 探针验证 → 失败 exit 1。
- 包内脚本是**独立副本**，不能 source 仓库里的 `lib/`（服务器上只有这一个包）。共享逻辑要在打包时内联，并在源码里注释"与 xxx 保持同步"。
- 体积优化（依赖下沉 / 瘦包）只在"包太大或启动太慢"时做。做了就必须写清切换顺序，例如：先 `load` 新基础镜像 → **删旧容器**（restart 不换镜像）→ 再发瘦包；顺序反了就是一次事故。

## 7. 常见的"看起来没问题"陷阱（都是真实事故）

| 陷阱 | 症状 | 防线 |
| --- | --- | --- |
| 只 `compile` 没重新打 jar | 包能发，功能是旧的 | 打包前强制 `clean package`；版本号从 jar 内读 |
| 版本号从源码算 | 旧包"自证清白" | `version.txt` 取自包内产物，`verify-build` 再比对源码 |
| `restart` 换基础镜像 | 依赖还是旧的 | 换镜像必须 `rm` 容器再 `run` |
| 挂载路径少了尾斜杠 | 拼出 `bbsUploadcommon` 之类目录，上传 404 | 统一 `${DIR%/}/`，并加探针 |
| `.env` 还是占位密码 | 容器反复重启 | 部署前显式比对占位符，命中直接中止 |
| Windows 编辑的 `.env` 带 CRLF | `source` 失败 | `sed -i 's/\r$//'` 后再 source |
| 验证前就归档 | 出事后找不到包 | 成功才 `mv` 到 `archive/`，失败原地保留 |
| 前端并行构建 | OOM | 串行 + `NODE_OPTIONS=--max-old-space-size=4096` |
| 打包前不停开发栈 | `mvn clean` 与 devtools 抢 `target/` | 停栈→构建→`try/finally` 恢复，判据是端口重新 listening |
| JVM 不设 `-Xmx` | 大内存机器默认堆过大，启动即崩 | 显式 `-Xmx`，别依赖默认值 |
| 迁移脚本不能重放 | 升级库正常、全新安装报 `Duplicate column` | 加列前查 `information_schema` 再 `PREPARE`；init 与 upgrade 两条路径各验一次 |
| 数据库"备份"只有同库 schema | 容器重建一起消失 | 区分"迁移前快照"和"灾备导出到宿主/对象存储" |
| 脚本只在 TTY 下能跑 | CI / 远程执行卡在 `read` | 交互处判断 `[ -t 0 ]`，并提供 `-y` |

## 8. 停止规则（命中就停下问人，不要自己决定）

- 同一问题连续 3 次尝试仍失败 → 停，写清现状与已试方案。
- 任何 `DROP` / `TRUNCATE`、对生产库写数据、执行 `init-*.sql` → 先问。
- 要改**已发布**的数据库迁移块 → 先问，只能新增。
- 要 `git push`、改 `.gitignore` / `.env` / CI 密钥 → 先问。
- 需求或验收标准有歧义 → 先问，不要按自己理解往下做。

## 9. 交付物与汇报格式

必须交付：
1. `scripts/` 分层脚本 + 根目录 `deploy.sh` 薄壳。
2. `SCRIPT.md`：目录结构、每个脚本的用法/退出码/判据、完整生命周期图。
3. 一张**验收命令表**（改了什么 → 跑什么 → 通过标准），例如：

| 改动范围 | 命令 | 通过标准 |
| --- | --- | --- |
| 后端代码 | `<build/test 命令>` | 全绿，用例数不低于基线 |
| 前端代码 | `<build 命令>` | 0 error，产出 dist |
| 数据库迁移 | 启动后端 + 查迁移表 | 日志出现 `Migration applied: vNNN`，条数与表增量一致 |
| 发布物 | `verify-build.sh` | `FAIL=0` |
| 部署结果 | `verify-server.sh` | `FAIL=0` + 浏览器回归一次 |

4. 汇报时严格区分三档：**已验证**（命令 + 输出摘要 + 时间）/ **推测** / **未验证**。没跑过的命令不要写"应该没问题"。

## 10. 你的执行方式

1. 先给出现状清单和分阶段计划，等我确认后再写代码。
2. 每个阶段结束都跑一遍该阶段判据，并做一次"故意改坏 → 变红 → 还原"的自检。
3. 每完成一个可验证单元就提交一次，提交信息按模块分组。
4. 中途要停（换会话/换机器/等我答复）时，写一份交接：现状 / 上次验证（命令+输出摘要+时间）/ 已知坑 / 下一步。
