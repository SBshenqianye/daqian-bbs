## 0. 结论摘要（给下一位工程师）

1. 当前系统只有 `USER(1) / ADMIN(2) / SUPER_ADMIN(3)`，`/admin/**` 在 `SecurityConfig` 用 `hasAnyRole("ADMIN","SUPER_ADMIN")` 一刀切；除 `DictController`/`SystemConfigController` 共 6 个写接口的 `@PreAuthorize` 外，管理端几乎**没有方法级权限点校验**。
2. 现有“版主”只是 `bbs_board_moderator(user_id,label_id,status=1)` 数据范围，**部分模块已按板块过滤**（文章删除/审核、举报、违规、采纳、精华推荐），**另一部分仍全局**（文章列表/计数、精华设置、建议采纳、申诉、精华终审、工作台）。
3. 新增 `MODERATOR(4)` 不是“加一行枚举”即可：必须同时处理
   - `AccountRole`、`Permission`、`User#getAuthorities`、`SecurityConfig` 四层；
   - “有板块 / 无板块”两种运行态；
   - 系统管理模块必须对 MODERATOR 全面 403（默认拒绝）；
   - `UserService` 登录 channel、角色写入白名单；
   - 前端 `main.js`/`api.js` 的 `hasAdminRole()` 与 `adminStore` 的角色映射。
4. 数据库实测（本地 `bbs_db`）：`user_type=1` 有 **2126** 人，`2` 有 **3** 人，`3` 有 **1** 人，`4` 有 **0** 人；有效版主任职仅 **2 条**，且两名用户都是 `user_type=2`（ADMIN）。按已确认决策 6，**本次数据迁移实际升级 0 人**。
5. 最大风险不是 SQL，而是**“ADMIN 是否仍然板块内受限”**：已确认决策 6 写的是“ADMIN + 板块按 ADMIN 全局处理”，但现有代码把非超管 ADMIN 当作板块受限（`canModerateBoard` 只对 SUPER_ADMIN 放行全局）。这需要产品最终确认，见第 9 节 Q1。

### 1.1 已确认（不再推翻）

| # | 决策 | 对实现的直接影响 |
|---|---|---|
| D1 | 新增账号角色 `MODERATOR`，`user_type='4'` | `AccountRole` 增加枚举；`bbs_user.user_type` 为 `varchar(20)`，无需改类型 |

| D7 | 左侧导航分“业务管理 / 系统管理”，MODERATOR 只显示业务管理 | 权限点矩阵决定菜单；`Sidebar.vue` 已有分组与权限过滤，无需重构，只需保证 MODERATOR 的系统权限点为 false |
| D8 | 版主管理页支持“编辑板块”（增/删/调整），后端用差异更新接口 | 新增 `POST /admin/moderator/boards`，一次事务内 diff add/remove，幂等 |

### 1.2 本文档采用的默认解释（需产品复核，见第 9 节）

| 项 | 默认解释 |
|---|---|
| “ADMIN 全局” | ADMIN（非超管）也拥有全局数据范围，不再按板块过滤；只有 MODERATOR 受板块限制 |

## 3. 目标模型

### 3.1 角色与 Spring Security 权限

| user_type | AccountRole | Authorities | 可登录管理后台 |
|---|---|---|---|
| 1 | USER | `ROLE_USER` | 否 |
| 2 | ADMIN | `ROLE_USER` + `ROLE_ADMIN` | 是（全局） |
| 3 | SUPER_ADMIN | `ROLE_USER` + `ROLE_ADMIN` + `ROLE_SUPER_ADMIN` | 是（全局 + 特权） |
| 4 | MODERATOR | `ROLE_USER` + `ROLE_MODERATOR` | 是（板块范围，可无板块） |

> 关键约束：MODERATOR **不得**拥有 `ROLE_ADMIN`；否则 URL 级 `hasRole('ADMIN')` 会把它当管理员。

### 3.3 数据范围的两种角色

```java
// 伪代码：AuthorizationService 目标语义
boolean isGlobalAdmin(User u)  // ADMIN 或 SUPER_ADMIN
boolean isModerator(User u)    // MODERATOR
List<Integer> getActiveBoardIds(userId) // status=1 的 label_id

// 全局管理员：不追加板块过滤
// MODERATOR：追加 article_label_id IN (boardIds)；boardIds 为空 → 空结果，不查全表
// 写操作：
//   labelId 为空                     → 403 "无法确定内容所属板块"
//   MODERATOR 且 boardIds 为空       → 403 "尚未分配板块，请联系管理员"
//   labelId 不在 boardIds            → 403 "无权操作该板块内容"
```

**注意**：现有 `canModerateBoard` 对 ADMIN 也是板块受限。若按 Q1 的默认解释改为“ADMIN 全局”，需要同步修改：
- `ArticleController#requireArticleBoardScope`
- `ReplyController#approveAdopt` / `pendingAdopts`
- `ReportServiceImpl#filterVisibleReports` / `canReviewReport`
- `ViolationServiceImpl#filterVisibleViolations` / `requireViolationScope`
- `FeaturedRecommendationServiceImpl#recommend`
- 以及所有 `isSuperAdmin(...)` 分支改为“是否全局管理员”。

自审批策略（`SelfApprovalPolicy`）**不变**：普通管理员/版主仍不能审批自己的内容，超管豁免。

### 3.4 “有板块 / 无板块”行为矩阵

| 场景 | 菜单 | 列表接口 | 详情接口 | 写接口 | 前端 |
|---|---|---|---|---|---|
| MODERATOR + 1..N 板块 | 业务管理全部 | 仅板块内数据 | 板块内可看，跨板块 403 | 板块内允许 | 板块筛选只列自己的板块 |
| MODERATOR + 0 板块 | 业务管理全部（可见） | `200` + 空列表/`total=0` | 403 或 404（建议 403） | `code=403` + “尚未分配板块，请联系管理员” | 顶部横幅 + 空状态；不退出登录 |
| ADMIN/SUPER | 业务 + 系统 | 全局（按 Q1） | 全局 | 全局 | 现有行为 |
| USER | 无 | — | — | — | 无法登录 channel 02 |

### 3.5 鉴权链路（目标）

```text
JWT Filter（查库重建 Authentication）
  → URL 规则（/admin/** 允许 ADMIN/SUPER/MODERATOR）
  → 方法级 @PreAuthorize（系统管理仅 ADMIN/SUPER；业务允许 MODERATOR）
  → Service 权限点校验（Permission）
  → Service 数据范围校验（boardIds / 无板块专用提示）
  → 自审批策略
  → 业务落库
```

## 6. 迁移与回滚 SQL 草案（只写文档，不执行）

### 6.1 版本与执行约定

- 版本名：`v039-moderator-role`
- 执行者：`DatabaseInitializer` 启动时自动执行 `upgrade-*.sql` 中未记录的块；执行前会自动备份受影响表。
- 幂等要求：DDL 用 `MODIFY` / `COMMENT ON`；DML 用带条件的 `UPDATE`；重复执行结果一致。
- 双库要求：MySQL 与 PostgreSQL 分别维护，禁止混用语法。
- **先改代码还是先迁移**：建议“先发后端代码（能识别 4）→ 再启动触发 v039”。因为旧代码会把 4 当非法值降级为 USER（`AccountRole.fromUserType` 告警 + USER），迁移早于代码会导致版主登录后被当普通用户。
- **回滚顺序**：先回滚应用版本（去掉 v039 块）→ 再执行回滚 SQL → 最后删除 `bbs_schema_version` 记录。否则当前版本重启会重新执行 v039。

### 6.2 `v039-moderator-role` — MySQL（追加到 `upgrade-mysql.sql` 末尾）

```sql
-- @migration: v039-moderator-role 版主账号角色（user_type=4）
-- 目标：新增 MODERATOR 账号角色；把“有有效版主任职的普通用户”升级为版主。
-- 幂等：MODIFY 可重复执行；UPDATE 带前置条件，重复执行不改变结果。

-- 1) 列注释同步（类型不变，仍为 varchar(20)）
ALTER TABLE `bbs_user`
  MODIFY COLUMN `user_type` varchar(20) CHARACTER SET utf8 COLLATE utf8_general_ci
  NULL DEFAULT '1'
  COMMENT '用户类型（1：普通用户，2：管理员，3：超级管理员，4：版主）';

-- 2) 普通用户 + 有效版主任职 → 升级为版主
--    管理员(2)/超管(3) 保持原角色（决策 D6）；id=1 恒为超管，兜底排除。
UPDATE `bbs_user` u
SET u.`user_type` = '4'
WHERE u.`user_type` = '1'
  AND u.`is_delete` = 0
  AND u.`id` <> 1
  AND EXISTS (
      SELECT 1 FROM `bbs_board_moderator` m
      WHERE m.`user_id` = u.`id` AND m.`status` = 1
  );

-- 3) 清理空值/非法值（保留 4）
--    与 v037 同口径，但白名单包含 4，避免把版主洗回普通用户。
UPDATE `bbs_user`
SET `user_type` = '1'
WHERE `user_type` IS NULL
   OR TRIM(`user_type`) = ''
   OR `user_type` NOT IN ('1', '2', '3', '4');
```

> 注意：
> - 第 2 步只处理 `user_type='1'`，不会把 ADMIN 降级。
> - 若某环境希望“ADMIN+板块也转 4”，必须显式修改条件并先确认 D6。
> - `u.is_delete = 0` 排除已注销用户；如果产品希望保留其角色，去掉该条件即可。
> - 本库实测该列默认值为 `NULL`，而 `init-mysql.sql` 写的是 `DEFAULT '1'`；上面的 `MODIFY` 会把默认值统一为 `'1'`（应用层对 NULL 也按 USER 处理，行为不变）。若希望严格保持 `NULL`，去掉 `DEFAULT '1'` 子句。

### 6.3 `v039-moderator-role` — PostgreSQL（追加到 `upgrade-pg.sql` 末尾）

```sql

JOIN bbs_board_moderator m ON m.user_id = u.id AND m.status = 1
WHERE u.user_type IN ('2','3');

-- 6. 迁移记录
SELECT version, description, applied_at
FROM bbs_schema_version
WHERE version = 'v039-moderator-role';
```

PG 版把反引号去掉、`TRIM`/`COUNT` 语法不变即可；`SELECT ... FROM bbs_user u JOIN ...` 均可直接使用。

## 7. 五块实施拆分

> 建议顺序：A（角色基座）→ D（迁移）→ B（生命周期）→ C（前端）→ E（测试贯穿）。

### 7.1 块 A：后端角色基础

**目标**：`MODERATOR` 能被识别、能登录、能被正确授权；系统管理默认拒绝。

**涉及文件**

- `bbs-server/src/main/java/com/walker/config/security/AccountRole.java`
- `bbs-server/src/main/java/com/walker/config/security/Permission.java`
- `bbs-server/src/main/java/com/walker/config/security/SecurityConfig.java`
- `bbs-server/src/main/java/com/walker/pojo/User.java`
- `bbs-server/src/main/java/com/walker/service/AuthorizationService.java`
- `bbs-server/src/main/java/com/walker/service/impl/AuthorizationServiceImpl.java`
- `bbs-server/src/main/java/com/walker/service/impl/UserServiceImpl.java`
- `bbs-server/src/main/java/com/walker/controller/UserController.java`（可选：`/common/user/info` 增加 `role/permissions/boardScopes`，供会话刷新）
- 测试：`AccountRoleTest`、`PermissionMatrixTest`、`AuthorizationServiceTest`、`UserServiceTest`

**接口**

- `POST /common/login`（channel=`02`）允许 `user_type=4`；返回 `role=MODERATOR`、`permissions[]`、`boardScopes[]`
- `GET /common/user/info`（可选）返回同上字段，便于前端刷新
- 所有 `/admin/**` URL 放行 `MODERATOR`；系统 Controller 类级 `@PreAuthorize("hasAnyRole('ADMIN','SUPER_ADMIN')")`

**测试点**

1. `user_type=4` → authorities 恰好 `ROLE_USER` + `ROLE_MODERATOR`，**不含** `ROLE_ADMIN`
2. `Permission.codesFor(MODERATOR)` 与 3.2 表一致；系统权限点全部 false
3. channel `02` + `user_type=4` 登录成功；channel `02` + `user_type=1` 仍失败
4. MODERATOR 调系统接口 → `code=403`；调业务接口 → 通过 URL/注解层
5. `getUserIdsWithPermission(REPORT_REVIEW/ADOPT_REVIEW)` 包含 4
6. 现有 USER/ADMIN/SUPER 矩阵不回归

**风险**

- 最高风险：误发 `ROLE_ADMIN`；用单测锁死。
- 次高：先放行 URL、后补注解的顺序错误；建议同一提交内完成，或先加“系统路径黑名单”。
- 登录响应字段变化可能影响旧前端解析；只新增字段，不改旧字段。

**验收标准**

- 单测全绿；手工用 4 个账号（USER/ADMIN/SUPER/MODERATOR）登录管理端，MODERATOR 只看到业务菜单；直接调用系统接口返回 403。

### 7.2 块 B：生命周期（任命 / 撤销 / 编辑板块 / 无板块）

**目标**：版主身份与账号角色联动正确；支持差异更新；无板块态可用。

**涉及文件**

- `bbs-server/src/main/java/com/walker/service/BoardModeratorService.java`
- `bbs-server/src/main/java/com/walker/service/impl/BoardModeratorServiceImpl.java`
- `bbs-server/src/main/java/com/walker/controller/BoardModeratorController.java`
- `bbs-server/src/main/java/com/walker/mapper/BoardModeratorMapper.java`（按需）
- `bbs-server/src/main/java/com/walker/service/impl/UserServiceImpl.java`
- 测试：`BoardModeratorServiceTest`、`UserServiceTest`

**接口**

- `POST /admin/moderator/appoint`：`1 → 4`，`2/3` 不变；保留积分≥300、重复任职校验
- `POST /admin/moderator/dismiss`：只 `status=0`，不改 `user_type`
- `POST /admin/moderator/boards`（新增）：请求 `{ "userId": 123, "labelIds": [2,4,10] }`
  - 校验用户存在、板块存在
  - 计算 `add = 目标 - 现有有效`、`remove = 现有有效 - 目标`
  - `add`：优先复用 `status=0` 历史行（避免撞唯一键），否则插入
  - `remove`：`status=0`
  - 事务提交；返回 `{added:[], removed:[], kept:[]}`
  - 幂等：同一请求重复调用结果一致
  - 空数组：撤销全部板块，但保留 `user_type=4`
- `POST /admin/moderator/list`：建议支持 `keyword`，返回 `userType`、`boards[]`、`labelNames`

**测试点**

1. 任命普通用户 → `user_type=4`；撤销 → 仍为 4
2. 任命 ADMIN → 仍为 2；撤销 → 仍为 2
3. 编辑板块：加 1 个、删 1 个、保持不变；重复调用无新增行
4. 撤销最后一个板块 → 登录成功、`boardScopes=[]`
5. 无板块调用写接口 → 403 “尚未分配板块，请联系管理员”
6. 跨板块编辑/操作 → 403 “无权操作该板块内容”
7. 并发/唯一键：历史 `status=0` 行被正确复用

**风险**

- 事务边界：`user_type` 更新与 `bbs_board_moderator` 写入必须同一事务，否则出现半升级。
- 差异更新与唯一键冲突：必须先查 `findAnyByUserAndLabel` 再决定 insert/update。
- 撤销全部后仍保留 4 是产品决策，接口不要“顺手降级”。
- 奖励批处理按 `bbs_board_moderator` 走，不受 `user_type` 影响；但要确认无板块的 4 不会被统计。

**验收标准**

- 用 ADMIN 账号完成“任命 → 加板块 → 删板块 → 撤销全部 → 重新任命”全流程；每一步数据库与登录响应一致。
- 版主自己无法调用 `/admin/moderator/**`（403）。

6. 角色变更后未重登：后端立即生效，前端提示“权限已变更，请重新登录”（可选）

**风险**

- `hasAdminRole` 漏改 → 版主完全无法登录（阻断）。
- `adminStore` 的 fallback 权限给多了 → 菜单泄露；建议 MODERATOR 不使用 fallback。

**验收标准**

- 浏览器控制台无因权限字段缺失导致的异常。

### 附：本次审计使用的只读查询（可复现）

```sql
-- 角色人数
SELECT user_type, COUNT(*) FROM bbs_user GROUP BY user_type ORDER BY user_type;

-- 有效任职分布
SELECT u.user_type, COUNT(DISTINCT u.id) AS users, COUNT(*) AS rows_cnt
FROM bbs_board_moderator m
JOIN bbs_user u ON u.id = m.user_id
WHERE m.status = 1
GROUP BY u.user_type;

-- 有效任职明细
SELECT u.id, u.username, u.nickname, u.user_type, m.label_id, l.label_name
FROM bbs_board_moderator m
JOIN bbs_user u ON u.id = m.user_id
LEFT JOIN bbs_article_label l ON l.label_id = m.label_id
WHERE m.status = 1
ORDER BY u.user_type, u.id;

-- 历史失效任职
SELECT m.*, u.username, u.user_type
FROM bbs_board_moderator m
LEFT JOIN bbs_user u ON u.id = m.user_id
WHERE m.status <> 1;

-- 4 账号 / 非法值
SELECT COUNT(*) FROM bbs_user WHERE user_type = '4';
SELECT COUNT(*) FROM bbs_user
WHERE user_type IS NULL OR TRIM(user_type) = '' OR user_type NOT IN ('1','2','3','4');
```
