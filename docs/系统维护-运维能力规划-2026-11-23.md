> 本文回答：运维级别的维护动作哪些该进后台、哪些必须留在命令行，以及 PostgreSQL 库内备份的风险边界。

## 1. 边界（先定不做的事）

| 动作 | 是否进后台页面 | 结论依据 |
| --- | --- | --- |
| 备份清单 / 运行状态（只读） | ✅ 进 | 零副作用，排障刚需 |
| 触发一次「受影响表」库内备份 | ✅ 进（P1） | 复用现有迁移前备份逻辑，库内复制，不产生下载 |
| 全量导出并下载 | ❌ 不进 | 大库会撑爆请求；会话被盗即整库外泄；离线容器里没有 pg_dump 与挂载卷 |
| 一键恢复某个备份 | ❌ 不进 | 不可逆，恢复期间必须停写；误点即事故 |
| 版本回滚（应用） | ❌ 不进 | 应用回滚=部署旧包，属于发布流程 |
| 数据库版本回退 | ❌ 不进 | 迁移只有前进没有 down 脚本，退版本要人工决定数据取舍 |

长期留存必须离开这台机器：宿主机 cron `pg_dump` / 容器卷快照 / 异地拷贝。库内 schema 会随库、随容器一起消失。

## 2. 分期

### P0 只读（建议先做，风险为零）

1. **备份清单**
   - PostgreSQL：`information_schema.schemata` 里 `bbs_backup_yyyyMMdd_HHmmss`；
   - MySQL：`information_schema.schemata` 里 `<库名>_yyyyMMdd_HHmmss`；
   - 展示：名称、创建时间、表数、占用体积（PG 可用 `pg_total_relation_size` 汇总；MySQL 用 `information_schema.tables`）。
   - 页面必须标注：**自动保留最近 3 份，更早的会被下一次备份自动删除**（`MAX_BACKUP_COUNT=3`）。
2. **运行状态**：数据库类型/版本、当前库体积、前 10 张大表行数、最近 10 条迁移记录（`bbs_schema_version`）。
3. **权限**：`maintenance:read`（默认 admin+super）。

### P1 安全动作

1. 「立即备份受影响表」：复用 `DatabaseInitializer.backupAffectedTables` 的复制逻辑，抽成可调用的服务；
   - 命名与自动备份区分：`bbs_manual_yyyyMMdd_HHmmss`，**不参与自动 retention**；
   - 审计 `MAINTENANCE_BACKUP`；权限 `maintenance:backup`（默认仅超管）。
2. 页面只提供「创建」，**不提供删除**；清理备份仍由人工执行 SQL/脚本。

### P2 需另行评审

- 异步全量导出到服务器固定目录（不下发浏览器）、恢复演练脚本、发布回滚手册。均不进页面按钮。

## 3. PostgreSQL 库内备份的风险（重点）

现有实现（`DatabaseInitializer`）：

- 备份位置：**同一数据库内的新 schema** `bbs_backup_<时间戳>`，逐表 `CREATE TABLE ... AS SELECT`；
- 保留策略：`cleanupOldBackups()` 在**每次新备份前**执行，只保留最新 3 个；
- 删除范围：`DROP SCHEMA bbs_backup_* CASCADE`，且名称必须严格匹配 `bbs_backup_yyyyMMdd_HHmmss`（`isBackupName`），不会误伤业务 schema。

由此得出三条硬约束，页面上必须体现：

1. **备份不是永久的**：第 4 次备份会把最老的一份删掉。需要长期留存的，必须导出到宿主机/异地，页面只展示“还能看到几份”。
2. **页面绝不提供 DROP / 恢复**：恢复需要先停写、再 `DROP` 现网表/`TRUNCATE` 或整库重建，任何“一键”都是事故源。
3. **备份 schema 与业务库同生共死**：容器重建、换数据卷、`DROP DATABASE` 都会带走备份 schema。跨机器备份才是唯一的灾备。

另外两个实现注意点（P1 落地时写进代码注释）：

- 手动备份命名必须走独立前缀，且 `cleanupOldBackups` 的匹配范围要继续收紧，避免手动备份被自动清掉或反之误删；
- 备份体积随表增长，P1 需要加“备份前检查剩余磁盘”与失败告警，不能静默继续。

## 4. 部署时自动备份（待实现）

结论：**可行，而且比“记得手动导出”可靠**。部署是天然的时间点，且迁移是在应用启动时执行的，所以在重启前备份即可覆盖升级风险。

### 落点

`scripts/prod/package.sh` 生成的 `upgrade.sh`，在「1. 创建版本目录 / 切换软链 / 重启容器」之前插入「0. 部署前备份」。`offline.sh` 只是解包并执行包内 `upgrade.sh`，不需要改。

### 命令形态（实测环境：WSL 的 `bbs-postgres`，宿主机无 pg_dump）

```bash
$RUNNER exec "$BBS_PG_CONTAINER" pg_dump -h localhost -p "$BBS_PG_INTERNAL_PORT" \
  -U "$BBS_DB_USER" --no-owner --no-privileges "$BBS_DB_NAME" \
  | gzip > "$BBS_BACKUP_DIR/bbs_$(date +%Y%m%d_%H%M%S).sql.gz"
```

与 `scripts/prod/ops/pg-backup.sh` 的 `container` 分支一致；该脚本已能自动发现 `bbs-postgres`、自动验证，只是**目前没有任何地方调用它**。

### 默认参数（`.env` 可覆盖）

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `BBS_BACKUP_BEFORE_DEPLOY` | `true` | 设 `false` 才跳过（应急部署） |
| `BBS_BACKUP_DIR` | `$BBS_HOME/backups` | 宿主机目录，容器重建不丢 |
| `BBS_BACKUP_KEEP` | `30` | 按文件数保留，超出删最旧 |
| `BBS_BACKUP_MIN_FREE_MB` | `1024` | 低于此值中止部署并提示 |

### 硬要求

1. `set -o pipefail`：否则 `pg_dump` 失败会被 `gzip` 的退出码掩盖，生成空/半截文件还当成功。
2. 备份后 `gunzip -t` + 非空校验，失败即中止部署（fail-closed），只允许显式关掉。
3. 备份只写宿主机目录，**不进容器、不进 Web 根目录**（dump 含手机号/身份证等 PII，权限 `600`）。
4. 保留策略只删 `bbs_*.sql.gz` 且只在本目录内，不碰 `bbs_backup_*` schema（那是迁移前备份，另一套）。
5. 上传目录 `BBS_UPLOAD_DIR` 建议同一时间点 `tar` 一份（可选，默认关；体积可能很大）。

### 已知缺口

- `scripts/prod/ops/` 没有打进升级包（包内只有 jar/前端/upgrade.sh）。二选一：把 `ops/pg-backup.sh` 一起打包，或在 `upgrade.sh` 内联约 30 行备份逻辑。**推荐内联**，减少现场对脚本位置的依赖。
- 部署备份只覆盖“升级前”这个点；两次部署之间的日常增量仍需宿主级定时任务（cron/crontab 调用同一个 `pg-backup.sh`），这是另一件事。
- 备份在宿主机磁盘上；整机损坏仍需异地拷贝，脚本层面无法解决。

### 验收

- 在 WSL2 跑一次生成的 `upgrade.sh`：`backups/` 出现新文件、`gunzip -t` 通过、`BBS_BACKUP_KEEP=3` 时第 4 次只删最旧；
- 故意把 `BBS_PG_CONTAINER` 改成不存在的名字：必须中止部署并给出清晰提示，不能静默继续。
